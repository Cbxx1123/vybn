# Commands and flags

Building, running (the program's flags and its --demo scenes) and the self-test suites in detail. The short version is in CLAUDE.md.


The project builds with CMake, using the 64-bit TDM-GCC toolchain on this machine (`-Wall -Wextra`):

- `cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_C_COMPILER=C:/TDM-GCC-64/bin/x86_64-w64-mingw32-gcc.exe -DCMAKE_CXX_COMPILER=C:/TDM-GCC-64/bin/x86_64-w64-mingw32-g++.exe -DCMAKE_BUILD_TYPE=Debug`: configure into `build/`
- `cmake --build build`: compile shaders, compile and link
- `./output/vybn` (`output\vybn.exe` on Windows): run the app; it stays open until the window is closed. Flags: a `.vbp` path (open that project instead of the demo), `--dark` or `--light` (that mode for this run, over the saved look), `--silent` (master gain at zero; the track meters still move; exports are still rendered at unity master gain, since the fader is only for monitoring), `--size WxH` (window size, default 1440x900, at least 960x640), `--plugin-folder PATH` (also scan this folder for plugins, CLAP and VST3, this run only; `output/plugins` holds the test plugins), and `--demo NAME` to start with `menu` (the Edit menu), `project` (the Project menu), `settings` (the settings dialog) or `shortcuts` open, `new` (the new project dialog), `projectsettings`, `audioclip` (a generated take imported onto the first audio track and opened in the audio editor), `recordmidi` (records a phrase sent through the MIDI hub onto the Lead track, as if played on a keyboard, and opens the take), `browser` (the asset browser on the library's instruments), `appearance` (the theme customiser), `export` (the Export dialog), `exportmix` (queues the project's Mix preset into the temp folder as `VYBN demo mix.wav`, without asking, and shows the Exports panel), `exportrelease` (queues the Release preset's two targets into the temp folder under their own names and shows the Exports panel; with `--silent` they still render at unity gain, so the report reads about -14 LUFS), `undo` (deletes the first clip's notes, undoes it, and opens the Edit menu), `notetools` (the piano roll in A minor with the first bar selected, a muted beat, every instrument track's notes as ghosts and the first two bars looping), `steps` (an instrument track "Drums" with a two-bar beat opened in the step sequencer, its Kick row selected), `masterautomation` (the arrangement's master row with its volume lane and a Limiter's lane shown, the master's writing armed and the transport playing), `folding` (two groups nested round some tracks, the inner one folded, the transport playing), `sidechain` (a pad whose compressor is keyed by a muted kick track, the Devices tab showing it, the transport playing), `pluginsidechain` (the same with the test plugin Test Duck keyed by the kick; with `--plugin-folder output/plugins`), `flexible` (three tracks into Group 1, the first also sending to Group 2 and a return, the mixer showing, the transport playing), `unsaved` (New with an unsaved change, so the save prompt shows), `clip` (a clip selected), `pianoroll` (the first guitar clip in the piano roll), `effects` (a compressor, an EQ and a bypassed reverb on the first track and a limiter on the master, with the Devices tab showing), `open` (Project > Open's file dialog), `saveas` (Project > Save as's), `importaudio` (Import audio's, which picks several), `plugins` (Test Gain, an EQ and Test Faulty set to crash on the first track, the Devices tab showing; with `--plugin-folder output/plugins`), `plugininstrument` (Test Sine playing the Lead track, with Test Gain after it), `pluginsettings` (Settings on its Plugins page), `plugineditor` (the first instrument plugin installed, else Test Sine, playing the Lead track with its device view open on its interface), `picker` (the device picker choosing the Lead track's instrument), `device` (an EQ on the first track in its own device view), `synth` (the Lead track played by the built-in synthesizer, the Devices tab showing), `versions` (two saved versions, "First idea" and "With bass", and the Versions dialog), `recovery` (a session that ended without closing, with the demo project's tempo changed, and the "VYBN didn't close properly" dialog over the window), `drop` (a generated WAV dropped on the Drums track at bar 5 and a two-part MIDI file at 96 BPM in 3/4 on the Bass track at bar 3, as if dragged in from Explorer: the WAV lands on Drums, the MIDI on Bass and a new Bass line track, and the tempo question shows), `takes` (three passes over two bars on the Drums track, one generated WAV at three offsets, and three melodies on the Lead track, each comped from all three and its take lanes shown), `tempo` (a ramp from 100 to 140 BPM over four bars, then 90, with 7/8 from bar 5 and 6/8 from bar 7, the transport playing through them), or `transport` (plays the transport). The two autosave demos write into a fresh temp folder unless `VYBN_AUTOSAVE_ROOT` names one. They exist so screenshots can be taken without clicking. Starting the app opens the default audio output device and every MIDI input plugged in; the audio input (a microphone, by default) opens only once an audio track is armed or one is chosen in Settings. Nothing goes online until the browser's Online tab is opened (it then lists the selected source) or Download is pressed. The demo project's guitar tracks are audible when the transport plays, so use `--silent` with `--demo transport` when checking playback on someone else's machine.
- The app shows a loading screen first (`daw::Splash`), then keeps its main window hidden until it has drawn (the `UISystem` is made with `startHidden`; `onShown` closes the splash), so nothing appears blank.
- `VYBN_FRAME_STATS=1` (any value but 0) makes the app print one FRAME line a second to stderr for the main window: the frame rate (all frames, and presented), the average update (with its layout share), build and submit times, the average surfaces, texts, glyphs, images, draws, pipeline binds and KB of prims uploaded, then the draw caches' hits, misses and prims reused and the share of frames whose layout was skipped. Use it to check a demo's draw count, for example `VYBN_FRAME_STATS=1 ./output/vybn --demo transport`.
- `VYBN_VERIFY_CACHE=1` (any value but 0) makes every `DrawCache` paint even when its key matches, and compares that paint with the section it kept: the first time they differ it prints `DrawCache: <name> drew something else under the same key` to stderr. Use it after changing anything a cached view draws or any key, and run a demo with it for some seconds with some interaction (for example `VYBN_VERIFY_CACHE=1 ./output/vybn --demo transport`); it should print nothing. A message means a key misses an input the cache's paint reads, and the named view's key needs that input added.
- `tools/test.sh`: runs every self-test suite (`VYBN_TEST_EXE` names another build to run, such as `output/vybn-dev.exe` while the app holds `vybn.exe`) below, each as a process of its own and in parallel, longest first, and prints one table (suite, checks, skipped, ms) and a non-zero exit code if any failed; about 10 s. `--serial` runs them one at a time (about 30 s), `SUITE...` only those named, `--times` lists the slowest checks, `--logs DIR` keeps each suite's output. Three tiers, set by environment variables the runner sets from its flags: the fast tier (default) runs every assertion on inputs just big enough to prove it; `--full` (`VYBN_TEST_FULL=1`) runs them on the full-size inputs (the whole demo song with the real guitar library, a 160,000-note project; about 50 s); `--bench` (`VYBN_TEST_BENCH=1`) adds the benchmarks, which time and print INFO lines and assert nothing. The plugin suite runs alone after the rest, since its few-millisecond deadlines break under load. `tests/Harness.h` holds the shared `Checker` (every suite ends with `return c.finish("name")`), the tier switches and `Pacer`; docs/testing.md has the architecture, the measured times and the rules for new tests.

- `./output/vybn --render-selftest`: renders twenty-two scenes off screen (a hidden window and `Renderer::beginOffscreen`; nothing is shown): `shapes` and `shapes-dark` (every shape, elevation and finish, accent, ink and a scrim), `text` (every text style and tone, the alignments, a clipped line), `clips` (nested clips cutting shadows), `image` (a generated `ImageData` at its size, stretched, faded and clipped), `lines` (rows of Lines at widths 1 to 6 and angles 0 to 90 degrees, a row at opacity 0.3, polylines, a Line cut by a clip and a dot), `plots` (Line, Fill and Range plots: a sine, an envelope, a waveform, a 4096-value curve, a plot cut by a clip and a two-value plot), `controls` (a tree of the UI layer's controls), `arrangement`, `automation`, `tempo`, `tempo-hidden`, `takes`, `master`, `folding`, `pianoroll`, `tuning` and `steps` (the DAW's views on the demo project, `tuning` the piano roll's tuning lane with a note gliding up, one held down and one wavering, the arrangement's tempo and signature lanes hidden but in `tempo`; `automation` with a track's lanes shown, `tempo` with three markers, a ramp from 100 to 140 BPM, a drop to 90, and 7/8 then 6/8 bars in the lanes, the ruler and the grid, `tempo-hidden` the same with the lanes hidden (the ruler's marks), `takes` the Lead track's three MIDI take lanes open under it with a comp cut from all three, `master` with the master row's lanes shown: its volume and a Gain effect's level, `folding` the nested-groups project with Outer open round a folded Inner (its clip as a block in its row, "1 track folded") and a lane open on one nested track), `mixer` (`MixerView` on the demo with two returns and two groups, 1500 wide so the group's fold chevron shows: outputs, send bars, a pre-fader send, the first track outputting to Group 1 and also sending to Group 2 ("To Group 1 + 1" and a G2 bar), the master strip), `radial` (a track header's toggles opened as a radial menu), `waveforms` (`ArrangementView` on eight audio tracks, each a 48-beat clip of a generated 30-second sound), `synth` (the synthesizer's panel on its Init setting), `sidechain` (the Devices panel on a pad: a Compressor keyed by the Kick track with its "Keyed by Kick" line and Sidechain row, an EQ with none, and a Gate), `pluginsidechain` (the Devices panel on a pad with two of the test plugins loaded in their sandboxes through a `PluginManager` on `output/plugins`: Test Duck keyed by the Kick with its Sidechain row, and Test Gain, which has no sidechain port, without one; the picture waits for both to be ready) and `scroll` (a 2000-row `ScrollView`, which shows culling at work). One hidden window stays open for the whole run, so GLFW starts once (starting it enumerates the input devices, which on some machines takes most of a second, and every scene's window paid it before). With `VYBN_TEST_TIMES` (the runner's `--times`) it prints `TIME` lines for its slowest scenes and check groups. Scenes with a component tree run frames until the fingerprint holds still (at most 300) before drawing. Each picture is compared with its golden, `tests/render/<scene>.png`: it matches when every channel is within 2 of the golden's and no more than 0.05% of pixels are further off. A missing golden fails. `--update-goldens` writes every picture as its golden instead (only after the new pictures have been looked at and the change explained), and `--scene NAME` renders one scene alone. On a mismatch it writes `<scene>.actual.png` and `<scene>.diff.png` (the differences in red) to `%TEMP%\vybn-render` and names them in the FAIL line. Each scene prints an `INFO render NAME:` line (build ms, surfaces, texts, glyphs, prims with the lines and plots among them, draws, KB uploaded, submit ms and plot values), and the scenes with a component tree or a DAW view (`controls`, `scroll`, `arrangement`, `waveforms`, `pianoroll`, `steps` and `synth`) are also timed over 50 settled frames with `VYBN_TEST_BENCH` set (a benchmark, not run by default), with `INFO render NAME x50:` lines (their average build and submit ms, prims and KB, the draw cache hits and misses per frame and the share of frames whose layout was skipped). The draw section and draw cache checks run with no window: sections appended and nested, plot offsets, hashes, the counts and `takeTotals`, a changed key painting again, `reuse` and `invalidate`; the count checks run when `VYBN_VERIFY_CACHE` is unset, and the verifier's own check when it is set. Each of the eight DAW scenes (`arrangement`, `master`, `folding`, `waveforms`, `pianoroll`, `steps`, `synth`, `sidechain`) also runs one more frame in the same render, after its picture is taken, and that frame must draw from its caches: at least one hit, no misses, layout skipped (a SKIP when `VYBN_VERIFY_CACHE` is set, since every draw paints). The INFO lines are not pass or fail. Run it after changing anything in `src/ui/` drawing, the shaders, the Theme or a DAW view's draw.
- `./output/vybn --import FILE...`: copies an instrument into the sample library and exits (the same code as File > Import instrument): one `.sfz` with the samples it refers to, or audio files named by note.
- `./output/vybn --write-icon PATH`: writes the app's icon as a Windows `.ico` (16 to 256 pixels, as plain bitmaps) in the default look (Carbon, dark) and exits. It is the loading screen's logo and groove on a tile in the theme's base and accent colours (`src/daw/app/AppIcon.cpp`, which the splash draws its logo with too). `assets/icon/vybn.ico` is its output, embedded in the executable by `src/win/vybn.rc.in` (so Explorer and the taskbar show it before the window exists); regenerate it with `output/vybn --write-icon assets/icon/vybn.ico` after changing the drawing, then rebuild. While running, the window's own icon is made from the user's current theme (`DawApp::refreshWindowIcon`, every frame, so the taskbar follows View > Appearance as it is edited).
- The executable's own icon follows the theme too, once the app has ended: a file's embedded icon can't change while it runs, so `DawApp`'s destructor calls `scheduleExecutableIcon` (`src/daw/app/AppIcon.cpp`), which compares the icon drawn for the current theme with the one inside `vybn.exe` and, if they differ, starts `output/vybn-icon-patch.exe` (`src/win/IconPatch.cpp`, a console-less static program built with `main`). It waits for the app to exit, then overwrites the icon's images in the resource section byte for byte and writes nothing else (every image is checked first to be the same number of bytes: the icon is stored as plain bitmaps, whose size depends only on the size in pixels, not as PNG). Windows' `UpdateResource` is deliberately not used: it rewrites the file and a debug build lost 24 MB of symbols to it. Explorer is told with `SHChangeNotify` (the file, its folder, and the system-wide "icons changed" notice), but an Explorer window that was already open keeps showing the old icon whatever is signalled to it (checked: a refresh, going to another folder and back, the shell's notices, `ie4uinit` and replacing the file all failed, while a window opened afterwards shows the new one). The helper leaves such windows alone (closing and reopening them was tried and dropped as too intrusive); closing and reopening the folder window shows the new icon. A pinned taskbar button or a desktop shortcut may also show the old icon until Explorer restarts. A rebuild puts the default icon back until the next exit. A read-only install just isn't patched. `main` also takes its own console off the taskbar (`keepConsoleOffTaskbar`, when it is the console's only user): Windows groups a console window with the app's window in one taskbar button that shows the executable's icon, not the window's.
- `cmake -E rm -rf build output`: clean

The VS Code tasks in `.vscode/tasks.json` wrap these: `configure`, `build` (default build task, depends on `configure`), `build & run`, and `clean`. The `Debug` launch config runs `build` before launching `output/vybn.exe`.

There is no test or lint target; the UI is checked by running the app and looking at it, and its drawing is checked against the render self-test's golden images. To check a single file, run `g++ -std=c++17 -Wall -Wextra -fsyntax-only -Isrc src/engine/Renderer.cpp`.
