# Overview

What VYBN is and how its parts fit together. The modules have pages of their own beside this one.


A C++17 neumorphic UI engine, the base for a DAW. An environment layer (`src/env/`) runs the program's systems as daemons. Today there are seven: the scheduler (`env::Scheduler`, the central manager of every worker thread, including the real-time pool that mixes tracks across cores), the audio system (`src/audio/`, on miniaudio with WASAPI on Windows), the memory manager (`audio::MemoryManager`, which keeps the first moments of long samples and audio clips in RAM and streams the rest from a disk cache), the resource manager (`env::ResourceManager`, which frees loaded instruments and sound files nothing uses), the plugin manager (`plugin::PluginManager`, the plugins found and every hosted instance's watchdog), the windowing system in the thin engine layer over GLFW and Vulkan (`src/engine/`), and the UI system in the UI layer (`src/ui/`). A plugin layer (`src/plugin/`) hosts CLAP and VST3 plugins, each instance in a sandboxed process of its own (`vybn-plugin-host.exe`): they play as instruments on instrument tracks and as effects in the track and master chains (as devices, like the library's instruments and the built-in effects), are listed in the device picker and the browser, show their own interfaces inside the app (drawn by the UI renderer from pictures captured in the sandbox, with the mouse and keys sent back) or as their own windows, have their latency compensated across tracks, and are managed in Settings > Plugins (folders, import, sandbox, turning them off, reloading). On top of them is the DAW's own UI (`src/daw/`). `src/main.cpp` only reads the flags, adds the daemons to an `env::Environment`, builds a `daw::DawApp` and runs it. On Windows the app replaces the system title bar with its own, a raised strip: the app's mark and name, a Project/Edit/Transport/View/Help menu bar (in one inset track) whose shortcuts the user can rebind, the project name in an inset pill (with a dot while unsaved), quick buttons for the browser, Appearance and Settings, and the window buttons. The look is dark by default (the Carbon preset) and customisable in View > Appearance. Below it are the transport bar (with record and the inputs in use), and a dock grid filling the rest: the arrangement over the mixer, the clip editor and the devices (each track's instrument and effects; tabs that can be torn off into windows of their own). Live figures (the audio load, threads, memory, frame times) are in Settings > Metrics. The asset browser (Tab) slides up over the bottom: the library's instruments and samples by category, and an Online tab that downloads more into it. Instrument tracks play MIDI notes and MIDI keyboards; audio tracks play sound files (imported, or recorded from the audio input). Both record. Return and group tracks (buses) play other tracks' sound: what tracks send them, and what tracks whose output they are play, with the master's volume part of the project. Every edit can be undone (Edit > Undo, Ctrl+Z), and Project > Export... renders the export presets to files in the background. A preset (saved with the project) is a list of targets: the master, the master without its effects, each track, chosen tracks, or MIDI; each target is a WAV, AIFF or FLAC file (or a MIDI file), normalized to a peak or to EBU R128 loudness, through a true-peak limiter, with fades, dither and the project's metadata. The render runs on an offline engine of its own, so the app keeps playing and editing while it goes; the queue is shown in the Exports panel, where each file has its measurements (integrated loudness, loudness range, true and sample peak, clipped samples) and a short-term loudness graph. `tests/` holds only automated checks. Text is drawn from a glyph atlas baked with stb_truetype from the bundled Inter font (`assets/fonts/`). Projects save to and open from `.vbp` files, which are TOML. Files are picked in the app's own file dialog (`ui::FileDialog`, a modal in the window), with Windows' dialogs as a fallback in Settings. There is no README or linter config. The only automated tests are the offline self-tests, run together by `tools/test.sh` (see `docs/testing.md`) (`main --audio-selftest`, `--project-selftest`, `--input-selftest`, `--notes-selftest`, `--engine-selftest`, `--browser-selftest`, `--plugin-selftest`, `--synth-selftest`, `--export-selftest` and `--render-selftest`).
