# Plugins (src/plugin/)

Plugins, CLAP and VST3, each hosted in a sandboxed process of its own. The user never has to know
which format a plugin is: one list, one set of folders, one way of adding them.


It depends only on the environment layer; the audio layer uses it (`PluginEffect`, `PluginInstrument`). Plugins, hosted out of process: native plugin code can't be contained in the app's own process, so every instance runs in `vybn-plugin-host.exe`, and a plugin may only use what the host deliberately offers. A crashing or hanging plugin costs at most one block of silence; the app and its audio thread go on.

- **`Protocol.h`** (shared by the app and the host, built by the same compiler): the control messages (`Message`: Scan, Load, Activate, Deactivate, Params, ParamText, SaveState, LoadState, Quit, Ping; Reply and Fail; the host's news Log, ParamsChanged, LatencyChanged, StateDirty) framed by `MessageHeader` and built and read with `Writer`/`Reader` (a short read leaves `ok()` false), `Descriptor` (id, name, vendor, version, description, url, features space-separated (CLAP's feature words; a VST3 plugin's subcategories are turned into them), path (a `.clap` file, a `.vst3` bundle or file); `instrument()`, `effect()`, `hasFeature`, `format()`, "clap" or "vst3" by its path (`isVst3Path`), never saved), `ParamInfo` (id, CLAP flags, name, module, min, max, default, value), `LoadedInfo`, and `Shared`, one instance's shared memory: the block's request (`request`/`done` sequence numbers, frames, planar stereo `input`/`output` of up to `kMaxFrames` 4096, the sidechain `key` (`keyChannels` of it, 0 for no key this block; `kProtocolVersion` 4: the Probe request since 3, the transport's signature, bar and tempo ramp since 4), `kMaxBlockEvents` (512) timed `Event`s (note on/off, all notes off, parameter values, controllers and the pitch bend), a `TransportInfo` (playing, tempo and `tempoPerSample` in a ramp, position in beats and seconds, the signature's numerator and denominator, and the bar with its start beat, all from the tempo map; the host fills CLAP's `tsig_num`/`tsig_denom`, `bar_number`, `bar_start` and `tempo_inc` from them)) and two `SharedRing`s of `ParamChange`s (the app's main thread to the plugin; the plugin's changes and gestures back). `SharedRing` is an SPSC ring that masks every index where it is used, so the other process scribbling on it can't make this one read outside it. The app treats everything the host writes as untrusted: counts clamped, indices masked, samples checked (NaN to 0, clamped to +-16), parameter ranges made finite, strings cut short.
- **`Sandbox.h/.cpp`**: `HostProcess::launch(exe, arguments, inherit, SandboxOptions)` starts the host suspended with only the listed handles inherited (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), in a job object (killed when the app closes it or dies, one process, a memory cap (`memoryLimit`, 4 GB), ends at once on a crash with no error box, no desktop, display or system settings, global atoms or exiting Windows), and in the AppContainer `VYBN.PluginSandbox` with no capabilities: no network, none of the user's files, registry or processes. The container is granted read and execute on the host executable, the plugin's file (a VST3 bundle's folder, with everything in it) and the `readable` paths (folders with everything in them), and write and delete too on the `writable` folders (`grantAccess`), by adding it to their access lists once (checked first, so nothing is added twice). Windows wants the container's profile before starting anything in it, so the first launch makes it (a registry key and an empty folder, `%LOCALAPPDATA%\Packages\vybn.pluginsandbox`). If the container can't be used the host runs in the job object alone and `contained()` is false with the reason in `note()`. The host's working folder is the system folder. `hostExecutable()` (beside the running program), `describeExit(code)` ("an access violation").
- **`Instance`** (`Instance.h/.cpp`): the app's side of one hosted plugin. `create(descriptor, options, error)` makes the pipes, the shared memory, two auto-reset events and a high-resolution waitable timer, launches the host and loads the plugin; `scan(path, options, found, error)` lists a plugin file's plugins in a host of its own (a plugin can crash just by being loaded), and `probeSidechain(path, id, options, channels, error)` asks one plugin's sidechain port in another (so a plugin that crashes when made costs only that call). Control calls (`activate(rate)`, `deactivate`, `params`, `paramText`, `saveState`, `loadState`, `close`) block until the host answers (spinning, then sleeping), with timeouts; one at a time (a lock); never on the audio thread. A control call that times out means the plugin's main thread is stuck: the host is stopped and the instance is `Hung`. Main thread: `setParam(id, value)` (through the ring, at the start of the next block, or flushed while inactive), `poll()` once a frame (the watchdog: the host ended is `Crashed` with its exit code; late for over `hangSeconds` (2 s; 10 offline) is stopped and `Hung`; then the host's news and the plugin's parameter changes), `takeChanges`, `takeLog`, `takeParamsChanged`, `takeStateDirty`, `status()`/`statusText()`, `latency()`, `contained()`/`sandboxNote()`. Audio thread: `process(ProcessBlock)` copies the inputs, events and transport (and the sidechain key, only when the block has one: `ProcessBlock::keys`/`keyChannels`) into the shared block, signals the host and spins for 50 us, then waits on the done event, the host's process handle and the timer, until 85% of the block's time (5 s with `setOffline(true)`). A late block plays silence and counts in `missed()`; until the host has finished it, later blocks don't wait at all; a host that ends wakes the wait at once. It takes no lock and allocates nothing (an event and a timer are kernel calls, like `Semaphore::release`). `active_` and `inProcess_` are a sequentially consistent handshake, so `deactivate` and `close` wait for the audio thread to leave `process` first.
- **The host program** (`vybn-plugin-host.exe <control-in> <control-out> <shared-memory> <process-event> <done-event>`, inherited handle values), in three parts. `host/HostMain.cpp` is either format's: the pipes and messages, the audio thread's wait, activation and restarts, the news, and the embedded interface's frame window, its capture and input. It makes a `Format` (`host/Host.h`: open, scan, probe, load, activate/deactivate, latency, params, paramText, state, guiEmbed/guiResize/guiOpen/guiClose, housekeeping, unload; and on the audio thread process and stopProcessing) by the file it is given: `.vst3` (a bundle or a file) is `host/Vst3Format.cpp`, anything else `host/ClapFormat.cpp`. **`ClapFormat`** loads one `.clap` (`LoadLibraryExW` searching only its own folder and the system's), creates the plugin with a `clap_host` offering only log, thread-check, params, audio-ports, note-ports, state, latency and gui (anything else gets null), and answers control messages on its main thread (the plugin's main thread; a reader thread feeds it, and it runs `on_main_thread`, `request_restart` (deactivate and activate again), param flushes while inactive and the news). Its audio thread (time-critical, denormals flushed) waits on the process event, builds the block's CLAP events (the ring's parameter changes at frame 0, then the block's, notes in the plugin's dialect, CLAP or MIDI, times kept in order) and transport, points the main ports at the shared buffers (other ports at silent scratch; a mono output is copied to both sides) and processes. A plugin's sidechain port, the first input port that isn't the main one with 1 or 2 channels (`Loaded::sidechainInput`), is pointed at the block's `key` when it has one (read in place, no copy) and at its own silent buffers otherwise, since a port must always have buffers. `Message::Probe` (path, id) makes and initialises one plugin and replies with that port's channels (`sidechainChannels`, the same rule as `buildPorts`); the app asks it in a host of its own, so a plugin that crashes when made costs only its probe. The plugin's output parameter events go back through the ring. The host exits on Quit or when its pipe breaks.
- **`Vst3Format`** (`host/Vst3Format.cpp`), written against Steinberg's interface headers alone (`vst3_pluginterfaces` 3.8.0, MIT; each interface's id an inline constant compared byte for byte, none of the SDK's code compiled). Opens a bundle's module (`Contents/x86_64-win/<its name>`) or a single `.vst3` file (`InitDll`, `GetPluginFactory`, `ExitDll` at unload). The factory's "Audio Module Class" classes are the plugins (names, vendor and version from `IPluginFactory3`'s unicode info, else `IPluginFactory2`'s), each with the id `vst3:` and its class id in hex; their subcategories become CLAP feature words (`Instrument|Synth` is "instrument synthesizer", `Fx|Delay` "audio-effect delay"; a class that says neither is an effect). Loading makes the component, then its edit controller: the component itself, or a class of its own (`getControllerClassId`) connected to it both ways through `IConnectionPoint` and given its state (`setComponentState`). The host offers `IHostApplication` (its name, and the `IMessage`s and `IAttributeList`s the two halves send each other), `IComponentHandler` and `IPlugFrame`. Activating makes every audio bus active, the main ones stereo where the plugin agrees, the first event input active, then `setupProcessing` (32-bit, realtime) and `setActive`; `setProcessing` on the audio thread's first block. A block: the app's parameter changes, the controller's edits and the block's own (at their frames) as `IParameterChanges`; notes as `IEventList` note on and off (all notes off as an off for each held key); controllers and the bend through the plugin's `IMidiMapping` (read into a table at activation) as the parameters they drive; the transport as a `ProcessContext` (positions in quarter notes); the main buses on the shared buffers, the sidechain (the first other input with 1 or 2 channels) on the key, other buses on silent scratch; all of it made before processing, nothing allocated. Parameters as the app sees them: a stepped one (`stepCount` > 0) runs 0 to its step count, any other 0 to 1 (the normalised value); flags become CLAP's (stepped, enum for lists, periodic, hidden, read-only, bypass, automatable); texts from `getParamStringByValue`. Values travel three ways: what the processor got (the app's, automation's, the MIDI mapping's) to the controller after the block (`setParamNormalized`, on the main thread, through a ring); the controller's edits (`beginEdit`/`performEdit`/`endEdit`, its interface) to the processor in the next block and to the app as gestures and values, through the audio thread while the plugin is active (it alone pushes into the ring to the app then), straight to the app while not; the processor's output changes to the app and the controller. `restartComponent` becomes CLAP's news: a reload, a bus change or a latency change restarts it (and reports the latency), a parameter change asks for a rescan. Its state is both halves' in one blob of the host's own (`VYB3`, then the component's bytes and the controller's, each after its length), restored component first. Its editor (`createView("editor")`, HWND) is attached to the same embedded frame, sized by `getSize` and `IPlugFrame::resizeView`, resized from the app with `checkSizeConstraint`/`onSize`; floating, VST3 having no floating interface of its own, it is attached to a window of the host's (`VybnPluginWindow`, resizable when the editor is, closing it is `GuiClosed`).
- **`Slot`** (`Slot.h/.cpp`): one place a plugin plays (an effect in a chain, an instrument on a track), holding its instance and what the UI shows of it. Loading (waiting for the start-up scan first), reloading, re-activating at a new rate, loading a state and fetching value texts run as Interactive jobs, one after another, sharing a `Core` with the slot so a slot that goes away leaves them to finish; replaced instances close as Background jobs. The instance reaches the audio thread through one atomic pointer with a single-reader hazard pointer (`using_`), so `swapIn` lets go of an instance only once the audio thread is out of it. `State` Loading/Ready/Failed/Crashed/Hung with `message()`, `busy()`. What a project keeps is the plugin's `state` (opaque) and `values` (`ParamValues`, sorted `{id, value}`; `valueOf`, `setValue`), the parameters set since: `apply(values, state)` (cheap when nothing changed) sends changed values through the ring, and a value dropped from the list (the undo of a first change) loads the state (or the `baseline`, the plugin's own state fetched just after it loaded) again first. `retarget(id, name)` points it at another plugin (a generation number lets go of a load that finishes late); `reload()`. Main thread, once a frame: `update()` takes what jobs finished, the watchdog's verdicts and the plugin's own changes (shown at once; `takeChanges()` hands the non-read-only ones to the project; gestures held in its window make `gesturing()`). `params()`/`param(id)`/`paramsVersion()`, `text(id, value)` (the plugin's words, asked for in the background, a number until then), `captureState()` (for saving, waiting up to 3 s), `hasEditor()`/`editorOpen()`/`toggleEditor()`/`editorError()`, `canEmbedEditor()`/`openEmbeddedEditor()`/`embeddedEditorOpen()`/`editorOpening()`/`closeEditor()`/`readEditorFrame`/`sendEditorInput`/`resizeEditor`/`placeEditor`/`clipEditor`/`allowEditorToFront`, `latency()`, `missed()`, `setOffline`, `contained()`. Audio thread: `live()`, `process(block)`.
- **Plugin interfaces**: CLAP's gui extension, win32, in two ways. Floating: the plugin's own top-level window, made and shown inside the sandbox. Embedded (`LoadedInfo::embedded`; preferred where the plugin allows it): never parented into the app's window (that would tie the app's input queue to a sandboxed, possibly hung, thread). The host parents it to a frame window of its own, layered at 1/255 opacity (invisible), a tool window that takes the real mouse and keyboard. The app places that frame exactly over where it draws the plugin's picture and just above its own window in the stacking order (never topmost), itself, with asynchronous `SetWindowPos`, and only when it has moved or fallen below the app's window (touching its stacking order, even a move to where it already is, makes a plugin close its open menus) (from the AppContainer the app's windows can't even be seen, so the host can't stack against them; the app may move the sandbox's lower-integrity window). So the plugin behaves as in any host: real input and cursor, and its own menus, lists and dialogs (top-level windows of its own) open at once in the right place. A press in the interface brings the frame to the front (its window procedure, on `WM_PARENTNOTIFY`; the app calls `AllowSetForegroundWindow` for the host while the mouse is over the picture), so typing reaches the plugin. `GuiClip` cuts the frame to the part of the picture shown (a region set by the host on its own window, so a hung plugin can't stall the app). While one of the app's menus or dialogs covers the picture (`Context::overlayCovers`), or the view isn't shown, the frame stands aside, off the screen. The host captures the frame (a `BitBlt` of the window's own copy, which doesn't make the plugin redraw; `PrintWindow` when that comes out one flat colour, as it does off the screen) 60 times a second for a second after input and 25 otherwise into a `GuiFrame` (shared memory the app makes per instance and hands over with `DuplicateHandle`: up to `kGuiMaxWidth` x `kGuiMaxHeight` (2560 x 1600) 4-byte pixels under a sequence lock) for the app to draw beneath it. The app's `GuiInput`s (move, down, up, double-click, wheel, leave, keys, characters) can still be replayed onto the plugin's windows. `Message::GuiEmbed` (the mapping's handle; replies with the size and the frame's window), `GuiInput`, `GuiResize`, `GuiClip` (no replies); `request_resize` resizes the frame. The host is per-monitor DPI aware, so its pixels are the app's. `Instance`: `openGui` (allowing the host's process to the foreground first)/`closeGui`/`guiOpen`/`hostProcessId`, and for embedding `openEmbeddedGui(w, h, error)`, `guiEmbedded`, `readGuiFrame(pixels, w, h, sequence)` (only when newer), `sendGuiInput`, `resizeGui`, `placeGui(x, y, shown, appWindow)`, `clipGui`, `allowToFront`; every pipe write takes `writeMutex_` alone (`send`), so input is never stuck behind a control call waiting for its reply. Limits: a plugin that draws with the GPU may capture black; a plugin that keeps presets or a database in the user's documents needs that folder granted for writing (Settings > Plugins), or may fail (Surge XT's patch search crashes without its `Documents\Surge XT`).
- **`PluginManager`** (`Manager.h/.cpp`): a daemon, added after the `ResourceManager` and before the `AudioSystem` (its effects and instruments hold plugins). `PluginConfig` (folders, `sandbox`, `disabled` ids (listed but never made: `create` says it is turned off), `grants` and `writeGrants` (folders each plugin may read, or also write in, by id, added to its `SandboxOptions`)), `config()`/`setConfig()` (takes effect for instances made after), `enabled(id)`, `waitForScan(ms)`, `setOffline(bool)` (every live instance, and new ones), `environment()`/`jobs()` (for slots), `standardFolders()` (`%COMMONPROGRAMFILES%\CLAP` and `\VST3`, `%LOCALAPPDATA%\Programs\Common\CLAP` and `\VST3`), `findPluginFiles(folder)` (`.clap` files, `.vst3` bundles (not searched inside) and `.vst3` files, two folders deep, as absolute paths: the host's working folder is the system's), `rescan(force)` (a Background job scanning each file in its own host, then asking each effect plugin's sidechain port with `Instance::probeSidechain` (`ScanStats::probed`; a failed probe leaves sidechain 0 and is remembered as probed, a forced scan asks again), `sidechainChannels(id)` (no copy, cheap every frame); the first file offering an id wins; a plugin in both formats (the same name and vendor) is listed once, as CLAP, and the other kept aside where `find` and `sidechainChannels` still reach it, for projects that use it; `scanning()`, `version()`, `plugins()`, `problems()`, `find(id)`, `lastScan()` (`ScanStats`: files, scanned, cached)). The scan cache: `PluginConfig::cacheFile` (the app's is `%APPDATA%\VYBN\plugins.cache`) remembers each file's size, time (a bundle's module's) and what it held (or why it failed, and each effect plugin's sidechain port, `Descriptor::sidechain` and `probed`: format 3, older caches read as empty and scanned again) as `ScanRecord`s (`readScanCache`/`writeScanCache`: tab-separated, escaped, written beside and renamed); unchanged files aren't loaded again unless `force` (Settings > Plugins' Scan again), and `create(id or descriptor, error)` (blocking; from a job), which it then watches: `tick` polls every live instance.
