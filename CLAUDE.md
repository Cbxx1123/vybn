# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

A C++17 neumorphic UI engine, the base for a DAW. An environment layer (`src/env/`) runs the program's systems as daemons. Today there are seven: the scheduler (`env::Scheduler`, the central manager of every worker thread, including the real-time pool that mixes tracks across cores), the audio system (`src/audio/`, on miniaudio with WASAPI on Windows), the memory manager (`audio::MemoryManager`, which keeps the first moments of long samples and audio clips in RAM and streams the rest from a disk cache), the resource manager (`env::ResourceManager`, which frees loaded instruments and sound files nothing uses), the plugin manager (`plugin::PluginManager`, the CLAP plugins found and every hosted instance's watchdog), the windowing system in the thin engine layer over GLFW and Vulkan (`src/engine/`), and the UI system in the UI layer (`src/ui/`). A plugin layer (`src/plugin/`) hosts CLAP plugins, each instance in a sandboxed process of its own (`vybn-plugin-host.exe`): they play as instruments on instrument tracks and as effects in the track and master chains (as devices, like the library's instruments and the built-in effects), are listed in the device picker and the browser, show their own interfaces inside the app (drawn by the UI renderer from pictures captured in the sandbox, with the mouse and keys sent back) or as their own windows, have their latency compensated across tracks, and are managed in Settings > Plugins (folders, import, sandbox, turning them off, reloading). On top of them is the DAW's own UI (`src/daw/`). `src/main.cpp` only reads the flags, adds the daemons to an `env::Environment`, builds a `daw::DawApp` and runs it. On Windows the app replaces the system title bar with its own, a raised strip: the app's mark and name, a Project/Edit/Transport/View/Help menu bar (in one inset track) whose shortcuts the user can rebind, the project name in an inset pill (with a dot while unsaved), quick buttons for the browser, Appearance and Settings, and the window buttons. The look is dark by default (the Carbon preset) and customisable in View > Appearance. Below it are the transport bar (with record and the inputs in use), and a dock grid filling the rest: the arrangement over the mixer, the clip editor and the devices (each track's instrument and effects; tabs that can be torn off into windows of their own). Live figures (the audio load, threads, memory, frame times) are in Settings > Metrics. The asset browser (Tab) slides up over the bottom: the library's instruments and samples by category, and an Online tab that downloads more into it. Instrument tracks play MIDI notes and MIDI keyboards; audio tracks play sound files (imported, or recorded from the audio input). Both record. Return and group tracks (buses) play other tracks' sound: what tracks send them, and what tracks whose output they are play, with the master's volume part of the project. Every edit can be undone (Edit > Undo, Ctrl+Z), and Project > Export... renders the export presets to files in the background. A preset (saved with the project) is a list of targets: the master, the master without its effects, each track, chosen tracks, or MIDI; each target is a WAV, AIFF or FLAC file (or a MIDI file), normalized to a peak or to EBU R128 loudness, through a true-peak limiter, with fades, dither and the project's metadata. The render runs on an offline engine of its own, so the app keeps playing and editing while it goes; the queue is shown in the Exports panel, where each file has its measurements (integrated loudness, loudness range, true and sample peak, clipped samples) and a short-term loudness graph. `tests/` holds only automated checks. Text is drawn from a glyph atlas baked with stb_truetype from the bundled Inter font (`assets/fonts/`). Projects save to and open from `.vbp` files, which are TOML. Files are picked in the app's own file dialog (`ui::FileDialog`, a modal in the window), with Windows' dialogs as a fallback in Settings. There is no README or linter config. The only automated tests are the offline self-tests, run together by `tools/test.sh` (see `docs/testing.md`) (`main --audio-selftest`, `--project-selftest`, `--input-selftest`, `--notes-selftest`, `--engine-selftest`, `--browser-selftest`, `--plugin-selftest`, `--synth-selftest`, `--export-selftest` and `--render-selftest`). Don't assume more structure exists than what is described below; check the tree first.

- The app shows a loading screen first (`daw::Splash`), then keeps its main window hidden until it has drawn (the `UISystem` is made with `startHidden`; `onShown` closes the splash), so nothing appears blank.
- `VYBN_FRAME_STATS=1` (any value but 0) makes the app print one FRAME line a second to stderr for the main window: the frame rate (all frames, and presented), the average update (with its layout share), build and submit times, the average surfaces, texts, glyphs, images, draws, pipeline binds and KB of prims uploaded, then the draw caches' hits, misses and prims reused and the share of frames whose layout was skipped. Use it to check a demo's draw count, for example `VYBN_FRAME_STATS=1 ./output/vybn --demo transport`.
- `VYBN_VERIFY_CACHE=1` (any value but 0) makes every `DrawCache` paint even when its key matches, and compares that paint with the section it kept: the first time they differ it prints `DrawCache: <name> drew something else under the same key` to stderr. Use it after changing anything a cached view draws or any key, and run a demo with it for some seconds with some interaction (for example `VYBN_VERIFY_CACHE=1 ./output/vybn --demo transport`); it should print nothing. A message means a key misses an input the cache's paint reads, and the named view's key needs that input added.
- `tools/test.sh`: runs every self-test suite (`VYBN_TEST_EXE` names another build to run, such as `output/vybn-dev.exe` while the app holds `vybn.exe`) below, each as a process of its own and in parallel, longest first, and prints one table (suite, checks, skipped, ms) and a non-zero exit code if any failed; about 16 s. `--serial` runs them one at a time (about 30 s), `SUITE...` only those named, `--times` lists the slowest checks, `--logs DIR` keeps each suite's output. Three tiers, set by environment variables the runner sets from its flags: the fast tier (default) runs every assertion on inputs just big enough to prove it; `--full` (`VYBN_TEST_FULL=1`) runs them on the full-size inputs (the whole demo song with the real guitar library, a 160,000-note project; about 50 s); `--bench` (`VYBN_TEST_BENCH=1`) adds the benchmarks, which time and print INFO lines and assert nothing. The plugin suite runs alone after the rest, since its few-millisecond deadlines break under load. `tests/Harness.h` holds the shared `Checker` (every suite ends with `return c.finish("name")`), the tier switches and `Pacer`; docs/testing.md has the architecture, the measured times and the rules for new tests.

## Architecture

### Environment layer (`src/env/`)

The program's runtime. It has no dependencies; the other layers depend on it.

- **`Daemon`** (`Daemon.h`): a system that runs for the life of the program. Its constructor takes the `Environment` first and finds the daemons it depends on with `env.require<T>()`; those must have been added earlier. `start()` runs when the environment starts; a daemon with its own thread (audio) starts it here. `tick()` runs once per loop iteration on the main thread, in the order daemons were added. `stop()` runs in reverse order; join threads here. Daemons are destroyed in reverse order, so a daemon's dependencies outlive it. `reportWait(ms)` reports time spent blocked (vsync, a device), so status displays don't count it as load.
- **`Environment`** (`Environment.h/.cpp`): owns the daemons. `add<T>(args...)` constructs `T(env, args...)`; `find<T>()`/`require<T>()` look them up by type. `run()` starts them, then loops until `requestStop()`. Each iteration runs posted actions, dispatches posted events, then ticks every daemon. `post(action)` is thread-safe, but takes a lock, so it is not for real-time threads. Posted actions and the event bus's posted events are each a `PostQueue`. `setWakeHook(fn)` (thread-safe `fn`, null to remove) is called after every `post` from the posting thread, so a loop sleeping in its event wait wakes at once: the WindowSystem installs `Window::wakeEventLoop` (`glfwPostEmptyEvent`) in its `start` and removes it in `stop`. `stats()` holds each daemon's busy time (average, peak) and waiting time, smoothed over about a second. `frame()` counts loop iterations.
- **`EventBus`** (`EventBus.h`, `env.events()`): typed events between daemons; any copyable struct is an event. `subscribe<E>(handler)` returns an id for `unsubscribe`. `publish(e)` delivers right away on the calling thread (main thread). `post(e)` can be called from any thread and is delivered at the start of the next iteration; it locks, so it is not for real-time threads. It also calls the wake hook (`setWakeHook`, set through the Environment), so a sleeping loop handles it at once. Handlers may subscribe and unsubscribe while being called; each event type's handlers are a shared list that `publish` holds while it delivers and that subscribing or unsubscribing copies only when a publish is holding it (copy on write), so a publish copies nothing. Handlers can run mid-input (when a menu action opens a window, say), so they should not change the UI tree directly: use `UISystem::post`.
- **`Signal<Args...>`** (`Signal.h`): a list of hooks an event is offered to, highest priority first and newest first among equals, until one returns true (handled); `emit` returns whether one did. `connect(handler, priority)` returns a move-only `Connection` that unhooks when destroyed (it may outlive the signal). Hooks may connect and disconnect, themselves included, during an emit; new ones wait for the next. The hook list is copy on write like the event bus's: `emit` holds it, and `connect` or a disconnect copies it only while an emit is holding it. Main thread only. The input system is built on it.
- **`PostQueue`** (`PostQueue.h`): work handed to the main thread from any thread, used by `Environment::post` and `EventBus::post`. `push(fn)` queues under a lock and calls the wake hook (`setWakeHook`); `drain()` runs what was queued, in order (what is pushed meanwhile waits for the next drain). Its two buffers swap, so a steady stream of posts allocates nothing once they have grown.
- **`ResourceManager`** (`Resources.h/.cpp`): the program's loaded resources in one place, a daemon added right after the `Scheduler`. Every pool of things kept in memory registers with it (`add`/`remove`; a `ResourcePool` has `poolName`, `usage()` (bytes and items held, and what nothing uses now) and `release(now, idleSeconds, wanted)`), and once a second (`sweep`) it lets go of what nothing has used for `ResourceConfig::idleSeconds` (Settings > Performance, 30 s by default), and of idle things at once, oldest first, while the pools together are over `budgetBytes` (512 MB). `trim()` lets go of everything unused now (Settings > Metrics' Free unused now); `stats()` per pool, with what each has let go. `ResourceCache<T>` is the usual pool: shared items by key (`find` (a use), `put`, `erase`, `keepIf`, `contains`) sized by a function, an item counting as in use while anything besides the cache holds it (`use_count() > 1`); its idle time starts at the last sweep that saw it held. The instrument library's sets and the `AudioPool`'s sound files are the two caches today. `resourceClock()` (seconds) and `processMemory()` (the process's private bytes, for Metrics) are here too.
- **`SpscQueue<T, Capacity>`** (`SpscQueue.h`): a fixed-size, lock-free single-producer/single-consumer ring buffer. `push`/`pop` never block or allocate, so they're safe on a real-time thread; `full()` (producer side) says whether a push would fail. This is how real-time threads talk to the main thread, since `post` and the event bus take locks.
- **`MpmcQueue<T, Capacity>`** (`MpmcQueue.h`): a fixed-size, lock-free queue for any number of producers and consumers (Vyukov's bounded queue); `push`/`pop` never block or allocate. The audio threads push disk requests on one that the Disk lane pops.
- **`Semaphore`** (`Semaphore.h/.cpp`): a counting semaphore. `release` takes no lock (one kernel call on Windows; a mutex and condition variable elsewhere), so a real-time thread may wake a worker; `wait`, `waitFor(ms)`.
- **`RealtimePool`** (`RealtimePool.h/.cpp`): worker threads for splitting real-time work across cores. `run(count, fn, context)` runs `fn(context, i)` for every `i` on the workers and the calling thread together and returns when all are done; it never locks or allocates. Jobs are claimed from one atomic ticket packing the batch number, its size and the next index (so a worker waking late can't take a job from another batch), and the caller takes any job no worker has reached, waiting only for jobs already under way. Workers sleep on a `Semaphore` between batches, and `run` wakes only those asleep (it counts them; the count and the ticket are sequentially consistent, so a worker going to sleep is either woken or sleeps through a batch the caller finishes), so a batch whose workers are awake makes no kernel call. When batches begin closer together than `kSpinWindowNs` (250 us: an offline render calling back to back), a worker that finishes one spins for the next instead of sleeping; at the live audio thread's pace (a block every few milliseconds) they sleep at once and never spin. `stop` drains wakes nobody took, so a restarted pool starts balanced. Workers run at time-critical priority with denormals flushed, and `setActive(n)` limits how many a batch wakes (and which may spin). One caller at a time. `RealtimePool(bool realtimePriority)`: `false` gives normal-priority workers (an offline engine's pool, which must not outrank the audio thread); `onWorkerStart(fn)` runs `fn` on each worker as it starts (set before `start`; an offline engine uses it to mark its workers as rendering offline).
- **`Scheduler`** (`Scheduler.h/.cpp`): the central manager of threads, a daemon added first. It owns the `RealtimePool` (one worker per core but one, up to 15, by default; `setRealtimeWorkers`) and the lanes: `Lane::Interactive` and `Lane::Background` share a pool of below-normal-priority workers (half the cores, at least 2; Interactive jobs first), `Lane::Disk` has two above-normal threads, `Lane::Network` four. `submit(lane, job, group)` from any non-real-time thread; `JobGroup` counts a set of jobs and `wait()`s for them (owners wait in their destructors); `runJob(env, lane, job, group)` uses the environment's scheduler, or a thread of its own when there is none (tests). Pollers (`addPoller(lane, fn, intervalMs)`, `removePoller`, which waits for a call under way) run whenever one of the lane's threads wakes: from `wake(lane)`, which real-time threads may call, or every interval; `fn` returns whether it did something, and is called again at once if so. Wakes coalesce: a lane's `wakePending` flag means only the first `wake` since its pollers last started signals a thread (otherwise it is one atomic exchange, so voices asking for many chunks make no kernel calls); a thread clears the flag before it runs the pollers, so a later wake always signals again. Each thread keeps its own snapshot of the poller list, taken again only when the list's version changes, and the shortest interval is cached, so running the pollers takes no lock; a removed poller is marked dead (`alive`, against its `running` count) and skipped until the snapshot is retaken. `onStop(hook)` runs at `stop()` before the threads are joined (downloads cancel there); jobs not yet started are dropped and count as finished. `stats(lane)`: threads, busy, queued, completed.

### Audio layer (`src/audio/`)

The real-time rule: code that runs on the audio thread (`AudioProcessor::process`, `AudioSystem::render` and what they call) must not lock, allocate, free or do I/O. It talks to the main thread only through atomics, `AudioParam`s and `SpscQueue`s.

- **`AudioSystem`** (`AudioSystem.h/.cpp`): the audio daemon. It is added after the `Scheduler` (whose real-time pool it uses when there is one; without one, as in some tests, it mixes on one thread) and before everything else in `main.cpp`, so it outlives the UI that shows it. `AudioSystem(env, Deviceless{})` is the deviceless engine (no miniaudio context, `devices()` empty, `start()` opens nothing, `lastError()` says it is offline) for exports and tests: its graph, transport, master gain and master effects work with `renderOffline`. It uses no pool until `setPool(pool)` gives it one (the scheduler's is the live audio thread's, one caller at a time; nullptr renders on one thread). `collectOffline()` deletes the processors the audio thread has let go of (`tick()` does it too).
  - It owns a miniaudio context (WASAPI on Windows) and a stereo f32 playback device, opened for input too (duplex) when `AudioSettings::input` names one; if the input won't open it plays without it, with a note in `lastError()`. The device opens in `start()` and closes in `stop()`. With no device it stays stopped with the reason in `lastError()`, and the program runs on.
  - `AudioSettings`: `device` (index into `devices()`, -1 for the default), `sampleRate` (0 for the device's), `bufferFrames` (a request: WASAPI shared mode usually gives about 10 ms) `exclusive` (falls back to shared if refused, with a note in `lastError()`) and `input` (`kNoInput`, -1 for the default, or an index into `inputDevices()`). `restart(settings)` and `stopDevice()` change them; `configure(settings)` restarts if running, else keeps them for `start()`. The open input: `inputName()`, `inputChannels()` (up to `kMaxInputs`, 8) and `roundTripFrames()` (input plus output buffer, what recordings are moved earlier by). Reported values are `deviceName()`, `sampleRate()`, `bufferFrames()`, `bufferMs()`, `backendName()` and `exclusive()`. It publishes `AudioDeviceStarted` and `AudioDeviceStopped` on the bus, from the main thread. If the device dies, the notification only sets a flag; `tick()` handles it.
  - The graph: `add<T>(args...)` constructs, prepares and owns a processor and queues an Add command. `remove(p)` queues a Remove. The audio thread applies commands at the start of each callback and sends removed processors back through a `retired` queue; `tick()` deletes them. While no device is running, the main thread applies commands itself. `active_` and the scratch buffers are sized up front (256 processors, 4096-frame blocks; longer callbacks are split), so the audio thread never allocates.
  - `render`: deinterleave the input into planar `AudioBlock::inputs` (metered: `takeInputPeak(channel)`); clear the planar scratch buses; every processor that isn't `parallel()` runs `process` in graph order (the MIDI hub, the metronome, the recorder, the previews), then the parallel ones (tracks, kept in `parallel_`, rebuilt when commands arrive) render at once across the pool (`renderParallel`) and are added in graph order (`mixInto`), so the result is the same on any number of threads; apply the smoothed `masterGain()` (linear, 0-1.5); meter; interleave into the device buffer; advance the transport. Each block starts with the transport's state and ends at the loop's end when it would cross it. It flushes denormals (SSE). Main-thread meters: `takePeak(channel)` (peak since the last call, so one reader), `load()` (processing time over buffer time, smoothed), `overloads()` (callbacks over budget) and `callbacks()`.
  - `renderOffline(out, frames, rate, input, inputChannels)` runs the same path on the calling thread while the device is stopped, with optional interleaved input. It's for tests and for the offline engines behind exports (`daw::OfflineEngine`, `RenderJob`).
- **`AudioProcessor`** (`AudioProcessor.h`): the graph's unit. `prepare(sampleRate, maxFrames)` runs on the main thread while the processor isn't being processed. `process(AudioBlock&)` runs on the audio thread and adds into `block.channels` (planar). The block carries the `TransportState`: playing, position in samples, tempo, and `beatAt(frame)`. Helpers: `AudioParam` (an atomic float with a range; `set`/`get` from any thread, `normalized()`/`setNormalized()` for sliders), `Smoothed` (a one-pole glide per sample, against clicks), `toDecibels`/`fromDecibels`. A processor that renders into buffers of its own and touches nothing shared returns true from `parallel()` and implements `renderParallel(const AudioBlock&)` (on any pool thread) and `mixInto(AudioBlock&)` (adds its result; audio thread); `process` must still do both.
- **Devices** (`Device.h/.cpp`, `DeviceChain.h/.cpp`): everything in a chain is a device: a track's instrument, then its effects (the master has effects only). `DeviceKind` Effect (a built-in effect, id its key, "compressor"), Sampler (a library instrument, id its name), Plugin (a CLAP plugin as an instrument or an effect, id its CLAP id) or Synth (the built-in synthesizer, an instrument, id `vibin.synth`). `DeviceSetting` is what the project keeps: kind, id, name, bypass, `values` (`plugin::ParamValues` by parameter id: a built-in effect has all of its (ids 0, 1, ...), a sampler its own, a plugin those set on top of its state; `value(id, fallback)`, `setValue`), a plugin's opaque `state` (not compared, so a new state alone isn't a change), `sidechain` (the id of the track an effect is keyed by, 0 for none: `uint32_t`, since the audio layer doesn't know daw's `ObjectId`; compared and saved) and `key()` ("effect:compressor", "sampler:<name>", "plugin:<id>", "synth:vibin.synth", what the catalogue knows it by); `deviceKindKey`/`deviceKindFromKey`. `DeviceParam` describes any parameter for editors (id, name, module, range, default, `ParamUnit` (None, Decibels, Hertz, Milliseconds, Ratio, Percent, Toggle, Choice, Semitones), log sweep, stepped, hidden, read-only, a choice's names), with `formatParam`, `paramToUnit`/`paramFromUnit` (the knob curve) and `pluginParam(plugin::ParamInfo)`. `Device` (main thread): `kind`, `matches(setting)` (same kind and id), `applySetting`, `update()` (once a frame), `params()` (a plugin's once loaded), `valueText(param, value)` (a plugin's own words), `slot()` (a plugin's `plugin::Slot`, else null), `latency()` (a plugin's while it plays; a bypassed effect's is 0), `hasMeter()`/`meter()`. Effects are `Effect`s (below); instruments are `InstrumentDevice`s (`Instrument.h`: an `Instrument` that is also a `Device`): `SamplerDevice` (`PluginInstrument.h/.cpp`: a `Sampler` with a Level parameter, `kLevel`, -6 dB by default; the app loads the library instrument and hands it to `sampler().setSampleSet`; `SamplerDevice::setting(name)`) and `PluginInstrument` (notes go to its slot with their frames in one call per block, its output added into the block, silent while loading or without a `PluginManager`; it counts the keys it holds, and all notes off releases each by key before the plugin's own all notes off, since Surge XT ignores a wildcard note off). `PluginEffect` (`PluginEffect.h/.cpp`) passes the sound through while the plugin loads (and when it can't be loaded, or without a manager), and is silent once it has crashed or hung or while it is late; it processes in place in pieces of at most 4096 frames with the block's transport (`pluginTransport`), handing its slot the chain's sidechain key (`Effect::setKey`) with each piece; `slotParams`/`slotValueText` are the plugin devices' shared descriptions. `DeviceChain` (one per track, `TrackProcessor::chain`, and the master's, `AudioSystem::masterEffects()`): `setPlugins(manager)`, `apply(instrument, effects)` (main thread; `DeviceKind::None` for no instrument; at most `kMaxEffects`, 8; a device whose setting still matches is kept with its state (a reverb's tail, a plugin's host), the rest made by `makeInstrumentDevice`/`makeEffectDevice`, prepared, and published with the new immutable `Layout` in one atomic store), `collect()` (main thread, once a frame: devices' `update`, and frees what `apply` replaced once the audio thread has finished two blocks since), `instrument()`, `effect(i)`, `device(index)` (`kInstrument`, -1, for the instrument), `latency()`; audio thread: `liveInstrument()` and `process(left, right, frames, transport)` (the effects), `setKey(effect, left, right)` (audio thread, for the next `process` only: the sidechain key of the effect at that index, forgotten when `process` ends, so a key the routing drops never lingers). `ChainInstrument` is an instrument track's NotePlayer's instrument: it plays whatever instrument its chain (`setChain`, atomic) has, read at the start of each block (a replaced instrument stays valid to the block's end), and forwards notes; the chain prepares and collects the devices. `Instrument::timedEvents()` (asked each block) with `noteOnAt`/`noteOffAt`: a `NotePlayer` then hands the block's notes to the instrument with their frames and processes the block once instead of splitting it (a split would cost a round trip to the plugin's host per note). `AudioSystem::prepareOffline(rate)` prepares the graph for an offline render now (so plugins can be waited for to settle at the export's rate). `DeviceChain::setOffline(bool)` (main thread) makes every plugin in the chain (the instrument's and each plugin effect's) wait for its load instead of passing the sound through, as an offline engine needs; devices made later by `apply` inherit it.
- **`Transport`** (`Transport.h`): lock-free play state, position and tempo. `play`, `stop`, `toggle`, `locate(sample)` and `setTempo` from any thread; the audio thread applies them at the start of each block and advances the position while playing. The loop: `setLoop(start, end)` (samples) and `setLooping(on)`; while looping, a block that would cross the loop's end is cut there (`framesBeforeLoop`, used by `render`) and `advance` jumps back to its start, so the jump lands on the exact sample (players see a jump, releasing their notes, and start those at the loop's start). Playing from past the end plays on.
- **`Processors.h/.cpp`**: `ToneGenerator` (sine; `frequency` and `gain` params, `enabled` atomic; fades in and out) and `Metronome` (clicks on each beat while the transport plays, higher on the bar's first beat; `gain`, `enabled`, `beatsPerBar`, `clicks()`). Both start disabled.
- **`Instrument`** (`Instrument.h`): the interface every instrument engine implements, an `AudioProcessor` that also takes `noteOn(key, velocity)`, `noteOff(key)` and `allNotesOff()` (audio thread, between process calls), `beginBlock()` (audio thread, start of each block, before notes: pick up main-thread changes here) and `collect()` (main thread, once a frame: free what the audio thread has let go of). Keys are MIDI numbers, 60 is C4. Controllers: `controlChange(controller, value)` (and `controlChangeAt` with a frame, for timed instruments): a MIDI controller 0-127 or `kPitchBend` (128), as 0-1 (the bend's middle 0.5); instruments ignore what they don't use. `ChainInstrument` and `SamplerDevice` forward them; the `Sampler` takes the mod wheel (1, vibrato at 5.5 Hz up to half a semitone), volume (7, 100 is unity) and expression (11) as a gain glided across each block, and the bend (two semitones each way), each voice's step multiplied once a block; `PluginInstrument` sends them as `plugin::EventKind::Controller` events, which the host turns into MIDI controller and pitch bend messages when the plugin's note port takes MIDI (`midiControllers`). New engines (synths) implement this and plug into a `NotePlayer`.
- **`Synth`** (`Synth.h/.cpp`, `SynthTables.h/.cpp`): the built-in synthesizer, an `Instrument` for `SynthDevice` (an `InstrumentDevice`; its kind is `DeviceKind::Synth`, so it is a catalogue entry ("VYBN Synth"), a project device and a track's instrument; its setting is the Init values, or a preset's with `setting(name)`). Parameters live in `audio::synth` (ids 0-105, never renumbered: Osc 1 and 2 (wave, shape, level, octave, semitones, fine, unison, detune, spread), sub and noise, the filter (LP12, LP24, HP12, band-pass, notch; cutoff, resonance, drive, envelope amount, key tracking, velocity), amp and filter ADSR envelopes, two LFOs (wave, rate or tempo sync, retrigger, fade in), six mod slots (source, target, amount) and the voice settings (Poly, Mono or Legato, voices, glide, bend range, drift, level); percent-style rows are stored 0-100 and read as 0-1, ms as seconds), and `synthParams()` lists them with the most useful first. `SynthTables`: a wave bank built once (`WaveBank::get()`, a function-local static) with the sine, triangle, saw, square, the basic, harmonic, vocal and PWM tables (16 frames each), every frame at 11 mip levels made by an inverse radix-2 FFT (`synth::fft`), level L holding the harmonics up to 1024 >> L; `levelFor(increment)` picks the level whose top harmonic stays below Nyquist. The engine: 16 preallocated voices, each with its two oscillators' unison copies (random start phases, a drift random walk, pan and detune spread evenly, gain 1/sqrt(n)), a sub (an octave or two down) and noise (a one-pole colour), two TPT state-variable filters per channel, two ADSR envelopes (60 dB per time), per-voice or shared LFOs, and a matrix applied every 16 frames (the oscillators and filters run per sample; increments and output gain glide across each step). Poly steals the quietest released voice, else the oldest; Mono and Legato keep a stack of the held keys and glide between them; the mod wheel, volume and expression, pitch bend, reset and all notes off are controllers. Parameters are copied from atomics at the start of each block (`beginBlock`), and nothing on the audio thread allocates.

- **`SynthPresets`** (`SynthPresets.h/.cpp`): the 24 factory presets (`synthPresets()`, `findSynthPreset(name)`), each with a category, a sentence and the values that differ from the defaults: Init; Bass (Sub Bass, Reese, Acid Line, Pluck Bass); Lead (Saw, Square, Vocal, Soft Sine); Pad (Warm, Glass, Strings, Dark Drone); Keys (Electric Piano, Organ, Digital Keys); Pluck (Bell, Synth, Mallet); Brass & strings (Synth Brass, String Ensemble); FX (Riser, Noise Sweep, Wobble). `SynthDevice::setting(name)` applies one and names it after it (an unknown name gives Init). Every preset but Init is a catalogue entry (`CatalogueEntry::preset`, source "VYBN Synth", in Bass, Keys or Synths); `CatalogueEntry::key()` adds "#<preset>" to the device's key, and `DeviceCatalogue::keyOf(setting)` gives a project's device the same key, which the pickers, the browser and the In use marks compare.
- **`Mastering`** (`Mastering.h/.cpp`, namespace `audio::master`): the export's mastering tools, run on background threads over chunks, never on the audio thread. `LoudnessMeter` (EBU R128: K-weighting (`kWeightingCoefficients`, the BS.1770 biquads at any rate), 100 ms chunks, momentary (400 ms), short-term (3 s), integrated with the -70 LUFS absolute and -10 LU relative gates, loudness range (EBU Tech 3342) and `shortTermSeries`; one double per 100 ms of memory), `samplePeak` and `TruePeakMeter` (4x oversampled with a 48-tap windowed-sinc interpolator, cutoff 0.45 of the rate, in dBTP), `TruePeakLimiter` (a 5 ms lookahead: the gain is the moving average over the lookahead of the least requirement in each window, so its attack is smooth and never overshoots, and it rises at the release rate (50-200 ms with the depth when `releaseMs` is 0); the output lags by `latency()` frames, `finish()` writes the rest, so the output is aligned to the input and has the same length), `Dither` (`DitherMode` None, Tpdf or NoiseShaped (second-order error feedback, 1.623 and -0.982), seeded) and `applyFade` (equal-power fades over a block at its position in the file).
- **`Encoders`** (`Encoders.h/.cpp`, namespace `audio`): the export's file writers. `makeWriter(EncodeFormat)` gives an `AudioWriter` for WAV, AIFF, FLAC or MP3 (`open` with the format and `AudioMetadata`, any number of `write`s of interleaved floats, then `close`), so memory stays bounded whatever the length. WAV is 16, 24 or 32-bit float, with a LIST INFO chunk (WAVE_FORMAT_EXTENSIBLE for 24-bit, float and more than two channels). AIFF is 16 or 24-bit big-endian, with an 80-bit extended rate and NAME, AUTH and ANNO chunks. FLAC is 16 or 24-bit and is our own encoder (RFC 9639): 4096-frame blocks, each channel as a CONSTANT, VERBATIM or FIXED subframe (predictor orders 0-4, residuals in 1 to 64 partitions of Rice codes with the parameter searched), the smallest of independent, left-side, right-side and mid-side stereo per block, CRC-8 headers and CRC-16 frames, a STREAMINFO whose sizes, total and MD5 of the samples are filled in on close (seeking back), and a VORBIS_COMMENT block (vendor "VYBN"; TITLE, ARTIST, ALBUM, COMMENT, DATE, ENCODER). Integers are clamped to full scale and rounded to the nearest step, with no dither (that's `Dither`, run first); 32-bit float is written unclamped. MP3 is the system's encoder (`Mp3Encoder.h/.cpp`: Media Foundation's MP3 encoder through a sink writer, Windows 8 and later, its DLLs loaded with `LoadLibrary` when an MP3 is first written so the program still starts on Windows N without the Media Feature Pack; MinGW's headers lack the MP3 container GUIDs, so they're defined there): constant bitrate from 16-bit samples, mono or stereo at 32, 44.1 or 48 kHz (`kMp3Rates`) and one of `kMp3Bitrates` (96-320 kbps; mono is capped at `kMp3MonoMaxBitrate`, 128, the encoder's limit). The encoder writes to `<path>.mp3part`; on close its ID3v2.3 tag is merged with ours (TIT2, TPE1, TALB, TYER, TSSE and COMM, Latin-1 or UTF-16; of its own frames everything else is kept, of its comments only `iTunSMPB`, the delay and padding for gapless playback) and the audio is copied after it into the part file. Decoders that ignore `iTunSMPB` (miniaudio) see about 1200 frames of delay at the start. Refused with a reason: 32-bit FLAC and AIFF, more than 8 channels, WAV or AIFF past 4 GB, and MP3 at another rate, bitrate or depth, or more than two channels. Everything goes to `<path>.part` and is renamed over `path` on close, replacing a file there; a failure removes the part file. Also `Md5` (RFC 1321, `md5Hex`), and `FloatTempWriter`/`FloatTempReader` (a render's target held as raw interleaved floats: a 24-byte `VBF1` header of channels, rate and frames, read back in order or from a seek).
- **`Automation`** (`Automation.h/.cpp`, namespace `audio`): parameters that change over the song. An `AutomationLane` is a parameter id and sorted `AutomationPoint`s (`beat` from the timeline's start, `value` a knob position 0-1 along the parameter's curve), straight lines between them (held for stepped parameters), flat before the first and after the last; a lane with no points is kept (shown) but plays nothing. The project keeps them in `Track::automation` (the track's own `kVolumeParam` and `kPanParam`) and `DeviceSetting::automation` (a device's parameters by id, so they move, copy and go with the device; compared by `operator==`). Helpers: `findAutomation`, `automationFor`, `automated` (has points), `setAutomationPoint`, `eraseAutomationPoints`, `thinAutomationPoints`. Recording a pass is `AutomationWrite` (`beginAutomationWrite` holds the lane's own value until a point `kGap`, 1/128 beat, before the touch; `writeAutomation` replaces the points since the last write with one at the playhead, moving the last point on while the value is held, and finishes and begins a new stretch when the playhead goes back; `finishAutomationWrite` puts the lane's own value back `kGap` after the pass when it had points and thins the pass alone). `ParamCurve` (min, max, logarithmic, stepped, `fader`: the volume's cubic taper) maps positions to values; `AutomationCurve` (a lane's points with its curve, `valueAt(beat)`) is what the audio thread plays. Devices opt in with `Device::automatable()` and take a value on the audio thread with `Device::automate(param, value)` before they run a block: built-in effects set their parameter atomics, the synth its stored parameters, the sampler its level, plugin effects and instruments queue a `ParamValue` event at frame 0 of their next block (sent through the host as a CLAP param event). `DeviceChain::setAutomation(devices, mix)` holds each device's curves (keyed by the device, so a device apply() keeps keeps its curves and one made new has none until set again) and the track's mix curves in its published `Layout`; `process` automates each effect at the block's start beat before running it, `automateInstrument` the instrument (called through `Instrument::automateBlock`, which `NotePlayer` calls before `beginBlock`), and `automateMix` gives `TrackProcessor` the volume and pan it uses in place of its fader's (the level glides a sample at a time). Values follow the transport's position playing or not, and exports render them (same bridge).
- **`SampleSet`** (`SampleSet.h/.cpp`): a multisampled instrument in memory: `SampleZone`s (key range, velocity range, root key, tuning and keytracking in cents, loop points, rate, gain, and the audio as mono or stereo interleaved 16-bit `pcm`, a `shared_ptr` shared by every zone that plays the same file; when the zone streams, `pcm` holds only the preload (`residentFrames()`) and `stream` (a shared `StreamSource`) the rest; `setSamples(floats)` fills it from floats, `kScale` turns it back) and a release time; immutable once loaded, shared by samplers. `zoneFor(key, velocity)` (the nearest zone if none covers it) and `zonesFor` (every zone covering it: layers). Loaders, for a background thread: `loadSfz` (a subset: `<control>`, `<global>`, `<master>`, `<group>`, `<region>`, `#include` and `#define`, block comments; `sample`, `key`, `lokey`, `hikey`, `pitch_keycenter`, `lovel`, `hivel`, `volume`, `amplitude`, `tune`, `transpose`, `pitch_keytrack`, `loop_mode` with `loop_start`/`loop_end`, `ampeg_release`, `default_path`; only the first round robin, the default keyswitch and attack regions are kept; more than `kMaxVelocityLayers` (4) layers are thinned to that many, and loading stops past `kMaxSampleBytes` (1 GB of 16-bit audio); each file is decoded once, straight to 16 bits into a buffer sized from its length, and near-silent tails (below about -78 dB) are trimmed with a short fade from files no zone loops), `loadNoteFolder` (files named like `E2.wav`; each covers up to halfway to its neighbours) and `loadInstrumentFolder` (its .sfz from `findSfz`, the shallowest within two folders, else note-named files). Each takes an optional `MemoryManager`: with one that streams, a long unlooped sample (trimmed, past the preload plus two chunks) is decoded once and written to the sample cache, keeping only its preload, and a sample the cache already has is read from there without decoding (`kMaxSampleBytes` counts what stays in RAM). `bytes()` is the RAM taken and `streamedBytes()` what streams. Decoding is miniaudio's (WAV, FLAC, MP3). `sfzSamplePaths` lists an SFZ's samples (and the files it includes) for copying it. `keyFromName`/`keyName` convert "C#4" and 61.
- **`Sampler`** (`Sampler.h/.cpp`): the sample engine, an `Instrument`. 48 voices with linear-interpolation pitch shifting, velocity (which picks the layer; every zone covering the key and velocity sounds, up to `kMaxLayers`, 4), loops, a release fade (the set's release time; -60 dB over it), stealing (the quietest releasing voice, else the oldest), and a re-struck key cuts its previous note in 10 ms, like a string. `gain` (AudioParam). `setSampleSet` (main thread) sends a set through a queue; the audio thread takes it in `beginBlock`, stops the old set's voices and hands the old set back, and `collect()` lets go of it, so sample memory is never freed on the audio thread. It returns false when the queue is full (no device running): try again later. Voices read through a `Segment` (a run of frames in memory: the preload, or one streamed chunk) found again when they leave it; a streamed zone asks for its first chunk at note on and for the next chunk whenever a voice enters one, and a voice that reaches a chunk not yet in memory plays silence for the rest of the block and keeps time (an underrun).
- **`MemoryManager`** (`Memory.h/.cpp`): the program's sample and clip memory, a daemon added after the `Scheduler` and the `AudioSystem` (its clock, `epoch()`, is the audio callback count). `MemoryConfig`: `streaming`, `preloadFrames` (32768, about 0.7 s), `chunkFrames` (16384), `budgetBytes` (128 MB), `idleSeconds` (20) and `cacheFolder` (the app uses `%LOCALAPPDATA%\VYBN\Sample cache`). The cache holds one `.vbs` file per sample (named by a hash of its path; a header with the path, the source's size and time, channels, rate and frames, then 16-bit audio: version 1), written beside it and renamed. `openCached(path)` and `create(path, pcm, channels, rate, error)` (loader threads) make a `StreamSource`: `preload`, `chunkCount`, and for the audio threads `chunk(k)` (the frames, or null, having asked for it) and `prefetch(k)`; never blocking. Audio clips stream 32-bit floats (`sampleBytes` 4, `preloadFloat`, `chunkFloat(k)`; half as many frames to a chunk, so they fit the same blocks): `openCachedFloat(path, trailer)` and `createFloat(path, channels, rate, read, trailer, error)` use a second copy, `<hash>-f.vbs` (version 2: the header, the trailer's length, the path, the floats, then the trailer, which holds the clip's overview), written a piece at a time from a `read` callback so a long file is never whole in memory; `openFloatFile(path, offset, channels, frames, rate, preload)` streams straight from a file that already holds floats (a recording's WAV). Floats rather than 16 bits for clips because recordings are float and may go past full scale, which 16 bits would clip, and an export has to match what was recorded; samples stay 16-bit (half the disk and pool), as they always were. `worthStreaming(frames)` (more than the preload and two chunks), `preloadFrames()`. The disk I/O pooler is a poller on the Disk lane (`poll()`, also callable directly): audio threads push `{source id, chunk}` on an `MpmcQueue` and `wake` the lane; its threads read chunks into fixed-size blocks (room for stereo) outside the manager's lock, up to the budget, evicting the chunk played longest ago when full (never one read in the last 8 callbacks, `kRecentEpochs`; only the current one while offline, since readers keep a chunk's pointer only for the block they found it in and an offline render is one call, so a render in big blocks through a small pool still finds room) and chunks unplayed for `idleSeconds`; spare blocks beyond 16 go back to the system. Readers stamp a chunk's use before taking its pointer and eviction takes the pointer before checking the stamp (sequentially consistent), putting it back if a reader just took it, so a block is reused at once without a reader still on it. Released sources (the last `shared_ptr` goes) wait in `dead_` until no read of theirs is under way; requests for them find their id gone. `setOffline(true)` (exports) reads a missing chunk on the rendering thread instead of playing silence, since offline renders outrun the disk. A source may outlive the manager (the `AudioSystem`'s processors are freed after it): its deleter reaches the manager through a shared `Lifeline` the destructor clears, and then only deletes the source. `stats()`: preload bytes, pool bytes, budget, sources, resident chunks, reads, evictions, underruns. `setRenderingOffline(bool)` / `renderingOffline()` (`Memory.h`, a thread_local flag) do the same for the calling thread alone: a deviceless engine sets it on its render thread and the workers of its pool, and the live audio thread never sees it (`StreamSource::chunk` reads a missing chunk there and then, and the eviction window of recent reads shrinks to the current callback).
- **`NotePlayer`** (`NotePlayer.h/.cpp`): plays a `NoteSequence` (notes in absolute beats, sorted by start) through an owned `Instrument`, in time with the transport: each block it finds notes starting and ending inside it and splits the block at their frames, so notes land on the exact sample. Stopping or jumping the transport releases everything; notes that began before playback aren't started mid-note. `setSequence` (main thread) swaps the sequence through a queue; the old one comes back and `collect()` deletes it; it returns false when the queue is full. `audition(key, velocity)`/`release(key)` play a key at once, for previewing. It is the source a `TrackProcessor` renders for an instrument track. With `setMidiSource(hub)` and `listen` set it also plays the hub's MIDI (note on/off, sustain pedal, all notes off, other controllers and the pitch bend passed to the instrument), releasing its keys when `listen` goes off. A `NoteSequence` also carries `controls`: `ControlCurve`s (a controller, points in beats, `stepped` for switches, `valueAt`); each playing block starts by sending every curve's value when it changed (in MIDI's steps; block-rate), except the sustain pedal (64), which the player keeps itself, holding the sequence's note offs (`pedalled_`) until it lifts; stopping or jumping puts the bend back in the middle, lifts the pedal and sends every value again.
- **Effects** (`Effects.h/.cpp`): stereo effect devices in a chain on a track (after its instrument, before its gain and pan) or on the master bus (before the master gain). The Gate and the Compressor have a "Detect HPF" (20 Hz to 2 kHz; at 20 Hz it is off and reads "Off", through `BuiltinEffect::valueText`) that high-passes what their detector hears, the key or their own input (`DetectorFilter`); the Gate compares its envelope with its thresholds as levels, and the Compressor skips its gain computer under the knee and takes its decibels with `fastDecibels`/`fastDbToLinear` (a log2 and exp2 from a float's bits and a rational fit, within a thousandth of a dB; checked against the std functions by the audio self-test). Nine built-in types (`EffectType`): Gain (level, phase invert), EQ (low shelf, mid peak with Q, high shelf), Filter (low-, high- or band-pass), Gate, Compressor (threshold, ratio, attack, release, soft knee, makeup, mix), Limiter (a 1.5 ms lookahead limiter with a final clamp at the ceiling), Saturation (soft, hard or fold, drive, mix, output), Delay (time, feedback, tone, ping-pong, mix) and Reverb (Freeverb: size, damping, width, mix). `effectInfo(type)` describes each (name, key (the device id), and up to `kMaxEffectParams` (8) `ParamInfo`s: name, key, range, default, `ParamUnit`, whether a knob sweeps it logarithmically, a choice's names), with `effectFromKey`, `effectSetting(type)` (a setting at the defaults) and `effectParam(info, id)` (as a `DeviceParam`). `Effect` (a `Device`): atomic bypass (any thread) and a gain-reduction `meter()`; `setKey(left, right)` (audio thread: the sidechain key for the next block, which Compressor and Gate, the effects whose `EffectInfo::sidechain` is true, detect on in place of their own input; `DeviceChain` sets it before `run` and clears it after); `run` (audio thread, with the block's transport) processes in place, fading to and from bypass over 10 ms, and starts from the parameters on its first block (so smoothed values don't glide from the defaults). `BuiltinEffect` adds the type and atomic parameters (`setParam`, `param`, by index), `makeEffect(type)` makes one. `kEffectTypeCount` (9). Biquads are RBJ's, in doubles, recomputed when a parameter moves; there is no oversampling (saturation can alias) and the limiter's lookahead isn't compensated.
- **`AudioData`** (`AudioFile.h/.cpp`): a sound file (mono or stereo interleaved f32 at its own rate) with a min/max overview per 256 frames (`range(from, to, low, high)` for drawing); immutable and shared. Short files are wholly in `samples`; long ones, when the `MemoryManager` streams, keep only the overview and the source's preload in RAM (`stream`, `streamed()`; `bytes()` counts what is in RAM). The audio thread reads either kind through `frameAt(index, span)` (a `Span`, the run of frames last found: the whole file, the preload or one chunk, started fresh each block since a chunk's pointer lasts one callback; null past the end or while a chunk isn't in memory, which asks for it and counts an underrun; entering a run asks for the chunk after it) and asks ahead with `prefetch(index)` (that chunk and the next). `loadAudioFile(path, error, memory)` (WAV, FLAC, MP3, for a background thread): with a streaming manager it reads the cache's float copy if up to date (no decoding), else decodes a long file a piece at a time into the cache, building the overview with a `PeakBuilder` as it goes (if the cache can't be written it loads whole). `makeAudioData(path, rate, channels, samples, memory)` (from samples in memory): a long recording whose file is their 32-bit float WAV (`floatWavLayout` finds where its audio starts) streams from that file and lets the samples go. `writeWavFile` (32-bit float by default; 24-bit, or 16-bit with triangular dither, clipped at full scale and converted a piece at a time).
- **`AudioClipPlayer`** (`ClipPlayer.h/.cpp`): an audio track's source. Plays a `ClipSequence` (`ClipRegion`s: start and end in beats, the data, the offset into it in seconds, gain, equal-power fade in and out in seconds) in time with the transport, resampled with linear interpolation and not stretched by tempo. `ClipSequence::crossfade(tempo)` gives overlapping regions fades across the overlap. Streamed data: each block, playing or not, every region under the playhead or starting within half a second asks for the chunks at the point it will play from (`kLookaheadSeconds`), so a clip starting mid-file (trimmed, or the playhead moved into it) finds its audio in memory; a frame whose chunk isn't there leaves that clip silent for the rest of the block, keeping time. The sequence is swapped through queues like NotePlayer's, so sample memory is freed on the main thread (`collect()`). `monitor`, `inputChannel` and `inputStereo` (atomics) pass the live input through, playing or not.
- **`SoundPreview`** (`Preview.h/.cpp`): plays one sound file from its start at once, whatever the transport does (the browser's previews); a streamed one reads through `frameAt` like clips, silent but keeping time where a chunk hasn't arrived. `play(data)`/`stop()` from the main thread swap it through a queue, the old one fading out in 8 ms; `collect()` lets go of what the audio thread handed back. `playing()`, `position()`, `gain`.
- **`MidiHub`** (`Midi.h/.cpp`): MIDI input. On Windows it lists and opens `midiIn` devices (`devices()`, `refresh()` (closes everything if the list changed), `open`, `close`, `isOpen`, `activity`, `openNames`); the driver's callback pushes channel messages into one lock-free queue per device (all eight slots exist from the start). As a processor, added before every track, it drains them each block into `events()` for listening NotePlayers, and stamps each with the transport's position for recording (`takeStamped`, main thread). `send(message)` injects one from the main thread (tests, demos, an on-screen keyboard later). Messages land at the start of their block.
- **`InputRecorder`** (`Recorder.h/.cpp`): captures every input channel into a lock-free ring (2^21 floats, 8 MB, made by `arm` and freed by `releaseMemory` once a take is drained and the audio thread is out of it: `inRing_` and `armed_` are a sequentially consistent handshake; `RecordingSession` frees it between takes) from the first block where it is armed, the transport plays and there is input, until disarmed; `startPosition()`, `channels()`, `capturing()`, `dropped()` (frames lost when the main thread falls behind), and `drain(out)` on the main thread.
- **Delay compensation** (`Track.h/.cpp`): `TrackProcessor::compensation` (atomic frames, at most `kMaxCompensation`, 16384) holds the track's sound back after its effects, through a delay line per channel (`kDelaySize`, 32768, a power of two) made in `prepare` and written every block, so changing it never allocates. `compensations(latencies)` gives each track what lines it up with the latest when every track goes to the master (tests). With routing, `daw::planRouting` works the delays out over the graph from each track's `trackLatency` (the plugin instrument's latency plus each plugin effect's not bypassed, while live): a track's input lines up with the latest of what feeds it, and every path (an output, a send) is held back by what its destination needs; a track's output delay is its `compensation`, each send's is in its `RouteSend` (the delay line is read at both). `AudioBridge::syncRouting` makes the plan again when the latencies (or the routing) change. A sidechain key is held back the same way: its delay is the keyed track's input time minus the source's output time (`RoutingPlan::Node::Key::delay`; the master's keys, the master's time minus the source's output), so the key lines up with the sound it keys.
- **Routing** (`Routing.h/.cpp`, namespace `audio`): where tracks' sound goes, as the audio thread plays it. A `Routing` lists the tracks (`Route`: the track's processor, its `output`, a bus's processor or null for the master, and its `RouteSend`s: the bus, the send's slot among the track's levels, its automation lane's id, its delay and pre or post fader) in stages (`stageEnds`), and `finish()` gives each bus its `Feed`s (the outputs and sends into it). `AudioSystem::setRouting` finishes it and hands it over through the command queue in order with adds and removes (so it must be replaced before a processor it names is removed; a remove of one the current routing names drops it, as a safety) and deletes it on the main thread once the audio thread has taken a newer one (`routingApplied_`). With a routing, `render` plays it stage by stage (`renderRouted`): the stage's tracks at once across the pool (`TrackProcessor::renderRouted`, a bus taking in its feeds before its effects: another track's output as it is, a send read from that track's delay line at the send's delay, times its fader's levels for post-fader or its mute's alone for pre-fader, and its level, which glides on the one bus it feeds, with automation from the track's mix curves through `DeviceChain::automateMixParam`). A gliding send level, and the mute ramp pre-fader sends use, count as settled within `kSettled` (1e-4, -80 dB) and are put there: `Smoothed` stops some 1e-5 short of its target in floats, so a tighter test never passed and every send ramped a sample at a time forever (a return taking in 24 sends: 64 us a block before, 8 us after), then the stage's tracks that go to the master added into it in order. With none (tests that add tracks themselves) every parallel processor goes into the master as before. A `Route` also has `keys` (`KeyFeed { from, effect, delay }`: sidechains, which order the source into an earlier stage and carry no sound to the master; at most `kMaxKeys`) and the `Routing` has `masterKeys`, which `AudioSystem::render` reads (`readKey` into four buffers of its own) once every stage has rendered, before the master effects run. `AudioSystem::masterVolume()` is the project's master volume, after the master effects and before the monitoring `masterGain`; `render` takes it at each block's start from the master chain's mix curves (`masterEffects_.automateMixParam(transport, kVolumeParam, volume)`) when the project's master volume lane has points, in place of the parameter's value.
- **`TrackProcessor`** (`Track.h/.cpp`): one mixer channel. It renders an optional owned `source` processor (given to the constructor; it can't change once the track is in the graph) into its own stereo bus, sized in `prepare`, runs its `chain`'s effects (the `DeviceChain`, whose instrument an instrument track's source plays), then applies `gain` (0-2, linear), `pan` (-1 to +1) and `mute` (atomic) in place, meters the result (`takePeak(channel)`, one reader) and adds it into the block. Under a routing it also fills up to `kMaxKeys` (4, `audio::kMaxKeys`) key buffers before its chain runs, from other tracks' delay lines (`readKey(delay, frames, left, right)`: the source's sound after its effects and before its fader, not silenced by its mute, read in at most two contiguous runs) and hands each to its keyed effect (`DeviceChain::setKey`). It is `parallel()`: `renderParallel` does the source, gain, pan and meter into the bus, `mixInto` the adding. Pan is constant power with a -3 dB centre (left `cos`, right `sin` of an angle from 0 to pi/2), applied to the source's left and right channels. Gain changes glide through `Smoothed`. The sends' levels are one atomic and one `Smoothed` per slot (`kMaxSends`, `audio::kMaxSends`, 64: 12 bytes a slot, `sizeof(TrackProcessor)` 1656 bytes, up from 1080 at 16); the project refuses more sends than that, so none is dropped. Solo goes through a shared `SoloGroup` (an atomic count of soloed tracks, held by each track through a `shared_ptr`): `setSolo(bool)` from any thread, and while any track in the group is soloed only soloed, unmuted ones are heard (`audible()`). A soloed track that is deleted releases its solo. `setTap(left, right, preFader)` (offline engines; main thread, while the track isn't processing; nullptr for none) copies every block's frames into the caller's buffers (each at least `AudioSystem::kMaxBlock` long) before the gain, pan and mute (`preFader`) or after them, which is exactly what the track adds into the mix; the live app never sets one, so it costs a null check.

### Plugin layer (`src/plugin/`)

It depends only on the environment layer; the audio layer uses it (`PluginEffect`, `PluginInstrument`). CLAP plugins, hosted out of process: native plugin code can't be contained in the app's own process, so every instance runs in `vybn-plugin-host.exe`, and a plugin may only use what the host deliberately offers. A crashing or hanging plugin costs at most one block of silence; the app and its audio thread go on.

- **`Protocol.h`** (shared by the app and the host, built by the same compiler): the control messages (`Message`: Scan, Load, Activate, Deactivate, Params, ParamText, SaveState, LoadState, Quit, Ping; Reply and Fail; the host's news Log, ParamsChanged, LatencyChanged, StateDirty) framed by `MessageHeader` and built and read with `Writer`/`Reader` (a short read leaves `ok()` false), `Descriptor` (id, name, vendor, version, description, url, features space-separated, path; `instrument()`, `effect()`, `hasFeature`), `ParamInfo` (id, CLAP flags, name, module, min, max, default, value), `LoadedInfo`, and `Shared`, one instance's shared memory: the block's request (`request`/`done` sequence numbers, frames, planar stereo `input`/`output` of up to `kMaxFrames` 4096, the sidechain `key` (`keyChannels` of it, 0 for no key this block; `kProtocolVersion` 3, the Probe request), `kMaxBlockEvents` (512) timed `Event`s (note on/off, all notes off, parameter values, controllers and the pitch bend), a `TransportInfo`) and two `SharedRing`s of `ParamChange`s (the app's main thread to the plugin; the plugin's changes and gestures back). `SharedRing` is an SPSC ring that masks every index where it is used, so the other process scribbling on it can't make this one read outside it. The app treats everything the host writes as untrusted: counts clamped, indices masked, samples checked (NaN to 0, clamped to +-16), parameter ranges made finite, strings cut short.
- **`Sandbox.h/.cpp`**: `HostProcess::launch(exe, arguments, inherit, SandboxOptions)` starts the host suspended with only the listed handles inherited (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), in a job object (killed when the app closes it or dies, one process, a memory cap (`memoryLimit`, 4 GB), ends at once on a crash with no error box, no desktop, display or system settings, global atoms or exiting Windows), and in the AppContainer `VYBN.PluginSandbox` with no capabilities: no network, none of the user's files, registry or processes. The container is granted read and execute on the host executable, the plugin's `.clap` and the `readable` paths (folders with everything in them), and write and delete too on the `writable` folders (`grantAccess`), by adding it to their access lists once (checked first, so nothing is added twice). Windows wants the container's profile before starting anything in it, so the first launch makes it (a registry key and an empty folder, `%LOCALAPPDATA%\Packages\vybn.pluginsandbox`). If the container can't be used the host runs in the job object alone and `contained()` is false with the reason in `note()`. The host's working folder is the system folder. `hostExecutable()` (beside the running program), `describeExit(code)` ("an access violation").
- **`Instance`** (`Instance.h/.cpp`): the app's side of one hosted plugin. `create(descriptor, options, error)` makes the pipes, the shared memory, two auto-reset events and a high-resolution waitable timer, launches the host and loads the plugin; `scan(path, options, found, error)` lists a `.clap`'s plugins in a host of its own (a plugin can crash just by being loaded), and `probeSidechain(path, id, options, channels, error)` asks one plugin's sidechain port in another (so a plugin that crashes when made costs only that call). Control calls (`activate(rate)`, `deactivate`, `params`, `paramText`, `saveState`, `loadState`, `close`) block until the host answers (spinning, then sleeping), with timeouts; one at a time (a lock); never on the audio thread. A control call that times out means the plugin's main thread is stuck: the host is stopped and the instance is `Hung`. Main thread: `setParam(id, value)` (through the ring, at the start of the next block, or flushed while inactive), `poll()` once a frame (the watchdog: the host ended is `Crashed` with its exit code; late for over `hangSeconds` (2 s; 10 offline) is stopped and `Hung`; then the host's news and the plugin's parameter changes), `takeChanges`, `takeLog`, `takeParamsChanged`, `takeStateDirty`, `status()`/`statusText()`, `latency()`, `contained()`/`sandboxNote()`. Audio thread: `process(ProcessBlock)` copies the inputs, events and transport (and the sidechain key, only when the block has one: `ProcessBlock::keys`/`keyChannels`) into the shared block, signals the host and spins for 50 us, then waits on the done event, the host's process handle and the timer, until 85% of the block's time (5 s with `setOffline(true)`). A late block plays silence and counts in `missed()`; until the host has finished it, later blocks don't wait at all; a host that ends wakes the wait at once. It takes no lock and allocates nothing (an event and a timer are kernel calls, like `Semaphore::release`). `active_` and `inProcess_` are a sequentially consistent handshake, so `deactivate` and `close` wait for the audio thread to leave `process` first.
- **`host/HostMain.cpp`** (`vybn-plugin-host.exe <control-in> <control-out> <shared-memory> <process-event> <done-event>`, inherited handle values): loads one `.clap` (`LoadLibraryExW` searching only its own folder and the system's), creates the plugin with a `clap_host` offering only log, thread-check, params, audio-ports, note-ports, state, latency and gui (anything else gets null), and answers control messages on its main thread (the plugin's main thread; a reader thread feeds it, and it runs `on_main_thread`, `request_restart` (deactivate and activate again), param flushes while inactive and the news). Its audio thread (time-critical, denormals flushed) waits on the process event, builds the block's CLAP events (the ring's parameter changes at frame 0, then the block's, notes in the plugin's dialect, CLAP or MIDI, times kept in order) and transport, points the main ports at the shared buffers (other ports at silent scratch; a mono output is copied to both sides) and processes. A plugin's sidechain port, the first input port that isn't the main one with 1 or 2 channels (`Loaded::sidechainInput`), is pointed at the block's `key` when it has one (read in place, no copy) and at its own silent buffers otherwise, since a port must always have buffers. `Message::Probe` (path, id) makes and initialises one plugin and replies with that port's channels (`sidechainChannels`, the same rule as `buildPorts`); the app asks it in a host of its own, so a plugin that crashes when made costs only its probe. The plugin's output parameter events go back through the ring. It exits on Quit or when its pipe breaks.
- **`Slot`** (`Slot.h/.cpp`): one place a plugin plays (an effect in a chain, an instrument on a track), holding its instance and what the UI shows of it. Loading (waiting for the start-up scan first), reloading, re-activating at a new rate, loading a state and fetching value texts run as Interactive jobs, one after another, sharing a `Core` with the slot so a slot that goes away leaves them to finish; replaced instances close as Background jobs. The instance reaches the audio thread through one atomic pointer with a single-reader hazard pointer (`using_`), so `swapIn` lets go of an instance only once the audio thread is out of it. `State` Loading/Ready/Failed/Crashed/Hung with `message()`, `busy()`. What a project keeps is the plugin's `state` (opaque) and `values` (`ParamValues`, sorted `{id, value}`; `valueOf`, `setValue`), the parameters set since: `apply(values, state)` (cheap when nothing changed) sends changed values through the ring, and a value dropped from the list (the undo of a first change) loads the state (or the `baseline`, the plugin's own state fetched just after it loaded) again first. `retarget(id, name)` points it at another plugin (a generation number lets go of a load that finishes late); `reload()`. Main thread, once a frame: `update()` takes what jobs finished, the watchdog's verdicts and the plugin's own changes (shown at once; `takeChanges()` hands the non-read-only ones to the project; gestures held in its window make `gesturing()`). `params()`/`param(id)`/`paramsVersion()`, `text(id, value)` (the plugin's words, asked for in the background, a number until then), `captureState()` (for saving, waiting up to 3 s), `hasEditor()`/`editorOpen()`/`toggleEditor()`/`editorError()`, `canEmbedEditor()`/`openEmbeddedEditor()`/`embeddedEditorOpen()`/`editorOpening()`/`closeEditor()`/`readEditorFrame`/`sendEditorInput`/`resizeEditor`/`placeEditor`/`clipEditor`/`allowEditorToFront`, `latency()`, `missed()`, `setOffline`, `contained()`. Audio thread: `live()`, `process(block)`.
- **Plugin interfaces**: CLAP's gui extension, win32, in two ways. Floating: the plugin's own top-level window, made and shown inside the sandbox. Embedded (`LoadedInfo::embedded`; preferred where the plugin allows it): never parented into the app's window (that would tie the app's input queue to a sandboxed, possibly hung, thread). The host parents it to a frame window of its own, layered at 1/255 opacity (invisible), a tool window that takes the real mouse and keyboard. The app places that frame exactly over where it draws the plugin's picture and just above its own window in the stacking order (never topmost), itself, with asynchronous `SetWindowPos`, and only when it has moved or fallen below the app's window (touching its stacking order, even a move to where it already is, makes a plugin close its open menus) (from the AppContainer the app's windows can't even be seen, so the host can't stack against them; the app may move the sandbox's lower-integrity window). So the plugin behaves as in any host: real input and cursor, and its own menus, lists and dialogs (top-level windows of its own) open at once in the right place. A press in the interface brings the frame to the front (its window procedure, on `WM_PARENTNOTIFY`; the app calls `AllowSetForegroundWindow` for the host while the mouse is over the picture), so typing reaches the plugin. `GuiClip` cuts the frame to the part of the picture shown (a region set by the host on its own window, so a hung plugin can't stall the app). While one of the app's menus or dialogs covers the picture (`Context::overlayCovers`), or the view isn't shown, the frame stands aside, off the screen. The host captures the frame (a `BitBlt` of the window's own copy, which doesn't make the plugin redraw; `PrintWindow` when that comes out one flat colour, as it does off the screen) 60 times a second for a second after input and 25 otherwise into a `GuiFrame` (shared memory the app makes per instance and hands over with `DuplicateHandle`: up to `kGuiMaxWidth` x `kGuiMaxHeight` (2560 x 1600) 4-byte pixels under a sequence lock) for the app to draw beneath it. The app's `GuiInput`s (move, down, up, double-click, wheel, leave, keys, characters) can still be replayed onto the plugin's windows. `Message::GuiEmbed` (the mapping's handle; replies with the size and the frame's window), `GuiInput`, `GuiResize`, `GuiClip` (no replies); `request_resize` resizes the frame. The host is per-monitor DPI aware, so its pixels are the app's. `Instance`: `openGui` (allowing the host's process to the foreground first)/`closeGui`/`guiOpen`/`hostProcessId`, and for embedding `openEmbeddedGui(w, h, error)`, `guiEmbedded`, `readGuiFrame(pixels, w, h, sequence)` (only when newer), `sendGuiInput`, `resizeGui`, `placeGui(x, y, shown, appWindow)`, `clipGui`, `allowToFront`; every pipe write takes `writeMutex_` alone (`send`), so input is never stuck behind a control call waiting for its reply. Limits: a plugin that draws with the GPU may capture black; a plugin that keeps presets or a database in the user's documents needs that folder granted for writing (Settings > Plugins), or may fail (Surge XT's patch search crashes without its `Documents\Surge XT`).
- **`PluginManager`** (`Manager.h/.cpp`): a daemon, added after the `ResourceManager` and before the `AudioSystem` (its effects and instruments hold plugins). `PluginConfig` (folders, `sandbox`, `disabled` ids (listed but never made: `create` says it is turned off), `grants` and `writeGrants` (folders each plugin may read, or also write in, by id, added to its `SandboxOptions`)), `config()`/`setConfig()` (takes effect for instances made after), `enabled(id)`, `waitForScan(ms)`, `setOffline(bool)` (every live instance, and new ones), `environment()`/`jobs()` (for slots), `standardFolders()` (`%COMMONPROGRAMFILES%\CLAP`, `%LOCALAPPDATA%\Programs\Common\CLAP`), `findClapFiles(folder)` (two folders deep, as absolute paths: the host's working folder is the system's), `rescan(force)` (a Background job scanning each file in its own host, then asking each effect plugin's sidechain port with `Instance::probeSidechain` (`ScanStats::probed`; a failed probe leaves sidechain 0 and is remembered as probed, a forced scan asks again), `sidechainChannels(id)` (no copy, cheap every frame); the first file offering an id wins; `scanning()`, `version()`, `plugins()`, `problems()`, `find(id)`, `lastScan()` (`ScanStats`: files, scanned, cached)). The scan cache: `PluginConfig::cacheFile` (the app's is `%APPDATA%\VYBN\plugins.cache`) remembers each file's size, time and what it held (or why it failed, and each effect plugin's sidechain port, `Descriptor::sidechain` and `probed`: format 3, older caches read as empty and scanned again) as `ScanRecord`s (`readScanCache`/`writeScanCache`: tab-separated, escaped, written beside and renamed); unchanged files aren't loaded again unless `force` (Settings > Plugins' Scan again), and `create(id or descriptor, error)` (blocking; from a job), which it then watches: `tick` polls every live instance.

### UI layer (`src/ui/`)

The UI has three layers. Keep their responsibilities separate:

1. **Styling: `Theme`** (`Theme.h/.cpp`). This is the only place visual values live, and it is strictly neumorphic. Every surface uses the background colour, and depth comes only from shadows. Shadow colours are derived from the base colour and are never set directly. Each setter clamps its value to a range where the effect still reads: base colour (saturation up to 0.25, lightness in the light 0.80-0.94 or dark 0.10-0.30 band; `setDarkMode` moves the same hue between them), accent, depth, softness, corner radius, shadow intensity, light angle (where the light comes from; 315 is top-left), curvature (strength of `Finish::Convex`/`Concave` face shading), rim (a fine lit edge toward the light on raised surfaces, away from it on inset ones, and a faint dark one opposite; 0-1), text contrast, font scale, spacing scale, and control scale (control heights, 0.8-1.2). Presets are `Theme::presetNames()`/`preset(name)` (Light, Dark, Ocean, Sand, Mint, Rose, Lavender, Graphite, Midnight, Carbon, Obsidian, Slate, Ember) and `fromColors(base, accent)`. `Color::toHsl` and `toHex` go the other way, for editors. `Theme::surface(rect, Shape, Elevation, depthScale, Finish)` resolves everything into a `Surface`, the main drawable primitive; `depthScale(Depth)` maps `Subtle`/`Normal`/`Deep` to a depth scale. Other surfaces: `accent()` (flat accent fill for state indicators), `ink()` (flat fill in a text colour, for icon strokes, with an optional opacity for faint grid lines), and `scrim()` (translucent base colour behind drawers). `Shape` is `Rounded`, `Soft` (smaller radius), `Pill`, `Circle`, or `TriangleRight`/`TriangleLeft`/`TriangleDown`/`TriangleUp`/`Cross` (flat fills for icons). Lines and plots are drawable primitives too, beside `Surface` and `Text`, and the theme makes them: `inkLine` and `accentLine` a `Line` (a straight stroke with round caps, `width` pixels thick, in a text tone or the accent, with an opacity), and `inkPlot` and `accentPlot` a `Plot` (a curve, filled curve or waveform drawn from values in one primitive, for a `PlotMode` of Line, Fill or Range, with an opacity). The caller then sets the plot's `values`, `count`, `low` and `high`, and the mode's `baseline`, `width` or `barFraction`. Components still never pick colours for them. Typography lives here too:
   - `fontSize(Size)` (13/15/18 px) and `fontSize(TextStyle)` (Caption 12 up to Display 44), both scaled by the font scale and snapped to a size baked into the atlas.
   - `textColor(TextTone)`. `Primary` is the base hue moved a contrast-sized step of lightness toward the shadow side: darker on light themes, lighter on dark ones. `Secondary` and `Muted` mix it back toward the base. `Accent` is the accent colour, and `OnAccent` is for text on an accent fill.
   - `mutedTextColor()` for disabled components, and `measureText()`.
   - The `Theme::text(...)` overloads resolve a `Text`, the second drawable primitive (string, baseline, size, colour), centred on the box by cap height.

   Every theme shares one `Font`, loaded on first use, so swapping themes keeps the atlas. `Theme::fingerprint()` hashes every value the theme holds and its font, so a cache or the layout can tell when the look changed. Don't let components choose colours, font sizes, or shadow sizes; add a theme method instead.
2. **Layout: `Container`** (`Layout.h/.cpp`). It stacks children in a row or column, with `Align`, `Justify`, and per-child `grow`/`alignSelf`, using two passes per layout (`measure`, then `arrange`). The gap is at least `Theme::spacing()`, and panel and root padding is at least `Theme::padding()`. Both are derived from the shadow extent (times the spacing scale), so neighbouring shadows don't collide. Users can add space but not remove it below those minimums. `gap()` and `padding()` are virtual so a container type can set its own minimum: `ListView` packs rows tighter because they have no shadow at rest. Containers lay children out by `preferredSize()`, which is `measure()` raised to `setMinSize()`. During a layout pass (`LayoutPass`, which `Context::layout` opens) each component's `measure()` result is kept and reused, so nested containers don't measure their subtrees again at every level (this took the Settings dialog from about 37 ms of UI time a frame to under 5). Nothing may change what a component measures while a pass is open; input and posted actions run between passes. `measure()` must not depend on `rect_`. `Grid(columns)` places children in cells row by row: each column is as wide as its widest child plus an equal share of spare width, and shrinks in proportion when there isn't enough. `Container::draw` skips a child whose rect, grown by 32 px, misses the clip and the window's bounds (an empty rect is always drawn, as it may not have been laid out). `Component::treeVersion()` counts changes to the shape of the tree, and `Component::treeChanged()` bumps it: `Container`'s `add`, `adopt`, `release` and `clear`, `ScrollView`'s `setContent` and `takeContent`, an overlay opening or closing, `Docking`'s moves of panels, and `ArrangementView`'s rebuild of its headers (any component that replaces children of its own calls `treeChanged()` too). `Context::update` lays out again only when the version has moved.
3. **Components**. A component only decides which surfaces and text to draw (elevation, shape, finish, depth, text style and tone). It handles the mouse from the frame's `Input`: position in framebuffer pixels, down/pressed/released this frame, `secondaryPressed` (right button; `mutable`, used up by the innermost `ContextMenuArea`), `middleDown`/`middlePressed` (the wheel button, for panning; the press is `mutable` and used up by the view that pans), wheel `scroll`/`scrollX`, `shift` and `mods`, time and `dt`, and `setCursor(engine::Cursor)` (the pointer's shape this frame: `Arrow`, `Hand`, `Crosshair`, `IBeam`, `ResizeX`, `ResizeY`, `Move`, `NotAllowed`; the last to ask wins, the arrow otherwise, and occluded input can't set it; `Context` hands it to `Window::setCursor` after the input pass). The wheel fields are `mutable`: the innermost `ScrollView` under the mouse zeroes them once used, so outer ones don't also scroll. Presses come from the window's events, so a click pressed and released between two frames still shows as a press, then a release next frame. The keyboard isn't in `Input`: it arrives through `input.signals`, the window's `InputSignals` (below), which components hook through a `Hooks` member. `Input` without signals (a closed drawer's content) means no keyboard for that component. `Input::ease()` gives frame-rate-independent smoothing for animation. `ClickState` (in `Component.h`) is the shared hover, press and click tracker.

   - `UISystem.h/.cpp`: `ui::UISystem`, the UI daemon (needs an `engine::WindowSystem` added first). Its constructor opens the main window through the WindowSystem, so the UI can be built before `run()`. Each window gets a `Context` with an app-drawn `TitleBar` (`titleBar()`) over a `body()` column, and the UISystem sets the window's caption test from the title bar. Extra windows (`openWindow`) share the main window's theme, copied every tick. They don't wait for vsync, so they never slow the main window. Minimised windows are skipped. Each tick updates every visible window and builds its frame, and presents it only when its fingerprint, framebuffer size or swapchain generation changed, or the window was refreshed (`Window::takeRefreshRequested`), was minimised, or asked for a redraw (`Context::requestRedraw`); a skipped frame costs no GPU work. The hidden main window draws until it has shown. It reports the renderers' blocked time as waiting, then runs posted actions. Then `pace` (the loop's pacing, which the next tick's event wait uses through `WindowSystem::setNextWait`): 0 when a window presented (vsync paces it), input waited in a window (`Window::hasEvents`, checked at the start of the tick), or a posted action ran; otherwise 1/60 s for half a second after the last of those, 1/30 s up to 3 s, then 1/10 s. `setBusy(true)` (DawApp, each frame: playback, recording and count-in, a render, a download, a preview, a plugin or sample set loading) keeps 1/60 s while nothing presents, so work that changes without input keeps its pace. `paceText()` ("active", "busy 60/s", "idle 10/s") shows in Settings > Metrics' UI frames line. On `engine::WindowClosing` it runs the window's `onClose` and destroys its Context, before the WindowSystem destroys the renderer. `popOut(floating)` moves a floating window's content into a native window, and closing that window docks it back. `openToolWindow(title, w, h, onClose, onCloseRequest)` opens a window the app places itself (hidden until shown, no caption dragging, the close button asking `onCloseRequest` first) and returns its `WindowParts` (id, window, context, title bar, body); `closeWindow(id)`, `releaseToolWindow(id)` (empties, hides and pools the window instead of destroying it). Every window draws on one shared Vulkan device and shares the UI's pipelines and font atlas, so a window costs its native window, its surface and its swapchain. Making a native window still takes about 0.2 s on this machine (a program here hooks window creation), so the UISystem keeps a pool of three hidden tool windows made behind the loading screen (`prepareSpares`; `kSpares`): `openToolWindow` takes one (sizing and naming it) and docking returns it, so a panel pops out and docks without a stall, and a fourth at once is made on demand. Spares are made small (160x120) with no swapchain (`WindowOptions::deferSwapchain`, set for every tool window): its first frame makes it at the window's size, and a spare back in the pool lets go of it (`Renderer::releaseSwapchain`). Spares aren't updated or drawn; the three cost about 4 MB together. The tick visits windows by index, so a callback may open a window (it draws from the next tick). `post(action)` runs after the frame. Menus, dropdowns and context menu areas open their popups in the window whose `Context` is running `update()` (`Context::active()`), falling back to the one they hold, so they work in content that moves between windows. `Context::toScreen`/`fromScreen` convert between a window's pixels and the desktop.

   - Don't add or remove children while the tree is handling input or drawing: use `Context::post` or `UISystem::post`. `Container::adopt`/`release` move components between containers, and `ScrollView::takeContent`/`setContent` move a scroll view's content.

Plumbing:

- **`Context`** owns the theme, the root container, the overlays and the `UIRenderer` for one window. `overlayCovers(rect)` says whether an open overlay that takes the mouse covers part of a rect. `engine::Window::nativeHandle()` is its HWND. Each frame, call `update()` (lays out only when it must, then input, callbacks, posted actions, clear colour), then `buildFrame()` (always lays out again, sets the DrawList's font and window bounds, fills the DrawList, and returns its fingerprint), and present only when the picture differs from the one on screen: `beginFrame()`, `submit()` (records the DrawList) and `endFrame()`. `render()` is build plus submit for any other caller. `requestRedraw()` presents the next frame whatever the picture. `ui::UISystem` does this for every window. `stats()` says what the last update, build and submit cost and drew (see `FrameStats`); `setPresented` records whether the frame went to the screen.
  - Overlays (`openOverlay<T>(OverlayOptions, args...)`, `closeOverlay`, `bringToFront`) sit above the root, newest on top. Each is arranged with the whole window rect and places itself.
  - Input goes top down. The topmost overlay under the mouse (by `Component::hitTest`) gets it; what it covers sees `Input::occluded()`, except that a drag already under way keeps the real mouse. A `modal` overlay blocks and veils everything beneath it. A `closeOnOutsideClick` overlay (menus) closes on a press outside it and uses that press up. Opening either clears the keyboard focus; they keep keys from what is under them with their own hooks.
  - Each frame `update()` takes the window's events: mouse buttons and the wheel go to the signals first (a hook can take them) and then into the frame's `Input`; the tree handles the mouse; then keys and text are dispatched through the signals in the order they were typed, so a click that focuses a text field comes before the keys typed after it.
  - Closing and `post`ed actions take effect after the input pass. The root fills the window and centres its children. `Context` sets the clear colour to the theme base every frame; neumorphism breaks if the background differs.
  - `update()` lays out only when `needsLayout()` says the rects on screen can't be used: the first frame, a change to `Component::treeVersion()`, a change to the window's size, or a change to the theme's `fingerprint()`. Otherwise input is hit-tested against the rects of the frame on screen, which are what the user is pointing at, and `stats().layoutSkipped` records the skip. A structural change made between frames bumps the version, so it is laid out before it gets input; other state changes (a posted action, a page shown) are laid out by the next `buildFrame`, as before. `buildFrame` always lays out, since callbacks may have changed anything.
- **`FrameStats`** (`FrameStats.h`) is what a window's last frame cost, read through `Context::stats()`: milliseconds of CPU for update (with its layout share), build and submit, whether the frame was presented, what was built (surfaces, texts, glyphs, images, lines, plots and the plot values) and what was submitted (draw calls, pipeline binds, bytes of prims uploaded). It also holds the last buildFrame's draw caches (`cacheHits`, `cacheMisses`, and `cachedPrims`, the prims the hits reused) and `layoutSkipped`, whether update skipped its layout. Submit's fields are 0 for a frame skipped as unchanged, and `batches` is always 0 now (kept for old readers). The render self-test, the Metrics page and `VYBN_FRAME_STATS` read it.
- **`Prim`** (`Prim.h/.cpp`) is the one GPU instance type, 80 bytes, the inputs of `shaders/prim.vert` (locations 0-4): `rect` (x, y, w, h in framebuffer pixels), `clip` (x0, y0, x1, y1 in whole pixels; nothing outside is drawn), `shape` (a Surface's radius, shadow distance, blur, and elevation with the rim's strength in its fraction; a Glyph's or Image's uv rectangle; a Line's ends `a` and `b`; a Plot's first value's index in the plot data, its count, and its `low` and `high`), `style` (a Surface's light direction, curvature and form; a Line's half width; a Plot's mode, its half width (Line) or bar fraction (Range), and its baseline (Fill)), and the colours as `uint32_t`s packed by `packColor` (red in the low byte, sRGB, rounded to 1/255): `base` (a surface's colour with its opacity in alpha, a glyph's colour and alpha, an image's opacity, a Line's or Plot's colour with its opacity in alpha), `light` and `dark` (a surface's shadow colours, their intensity in alpha), and `kind` (`PrimKind`: Surface 0, Glyph 1, Image 2, Line 3, Plot 4). `clipBounds` rounds a clip out to whole pixels (floor of its start, ceil of its end), or to plus or minus `kNoClip` on every side when unclipped. `surfacePrim` packs a Surface as the old `toInstance` did, `glyphPrims` appends one Glyph prim per visible glyph of a Text from `Font::layout`, and `imagePrim` makes an image's quad (uv 0 to 1, white with the opacity as alpha). `linePrim` makes a Line's prim, its rect the capsule's bounds grown by half its width (at least half a pixel) plus a pixel, and `plotPrim` a Plot's, its rect the plot's rect, with the index of its first value and its count as floats (exact below 2^24).
- **`DrawList`** (`DrawList.h/.cpp`) holds the frame as `Prim`s in drawing order (later on top, whatever their kind), in one vector that keeps its capacity between frames. `add(Surface)` adds one Surface prim. `add(Line)` adds one Line prim, and `addPolyline` one per segment of a run of points, each in the style's width, colour and opacity (a line of zero length is a dot of its width). `add(Plot)` adds one Plot prim and copies its values into `plotData()`, each Range's as low, high pairs, in the order added; a null `values`, or fewer than two values (one for a Range), adds nothing. `add(Text)` lays the string out there and then, with the `Font` that `setFont` gave the list (Context sets the theme's each frame; with no font, text draws nothing), one Glyph prim per glyph, keeping only those that draw something (an empty text adds nothing). `add(ImageDraw)` adds an Image prim and an entry in `images()` (the prim's index and the `ImageData`, which must outlive the frame's rendering), and nothing for an image with no pixels. `pushClip(rect)`/`popClip()` set the clip each prim carries, intersected with the one outside it and rounded out to whole pixels, so a clip never splits the list, and shadows are clipped too. Culling: `setBounds` (Context sets the window's area each frame) and each prim's clip reject a prim whose drawn area misses either (a raised surface's area is grown by its shadow, as `prim.vert` grows it, and a Line plot's by its half width; a Line's rect is already its capsule's bounds; edges that only touch don't count). `counts()` says what was added since `clear()`, for FrameStats (surfaces, texts, glyphs, images, lines and plots). `clear()` keeps the font and the capacity. `hash()` is the running hash: each prim's bytes and each plot's values are folded in as they are added (64-bit words, FNV-1a), so the fingerprint no longer walks the list. A plot's index is folded relative to its section's values, so a section hashes the same wherever it lands. Sections nest: `beginSection()` starts one, and `endSection(DrawSection &)` copies what was added since into it (its prims, its plot values rebased to start at 0, whether it holds an image, and its hash, which is then folded into the enclosing hash as one word; the prims stay in the list), while `appendSection` adds one again (rebasing its plot indices to where its values land, counting its prims, and folding its hash as one word). A section holding an image is never appended, since its `images()` entries aren't kept. `fingerprint(list)` is the running hash, then each image's prim index, id and version, so equal fingerprints mean the same picture, and a cached frame and a painted one with the same content give the same fingerprint. `clip(out)` and `bounds(out)` read the clip that prims added now would carry and the bounds, for cache keys.
- **`DrawCache`** (`DrawCache.h/.cpp`) keeps what a component drew while what it depends on stays the same: a repaint boundary, as in Flutter's or Chromium's paint chunks. A heavy view or small control holds one as a member and draws through it: `cache_.draw(list, theme, rect_, key, [&] { drawContent(list, theme); }, reuse)`. The `key` must cover everything the paint function reads (the store's revisions, scroll, zoom, hover...). The cache adds the rest itself: the rect, the list's clip and bounds, the theme's fingerprint and the font. While they all match the last paint's, the section kept then is appended again (`appendSection`) and counted as a hit; otherwise the paint runs, counted as a miss, and its section is kept. `reuse` false always paints (while recording, while a drag or a glide is under way, or while a control's state animates), and a section holding an image is never reused. `invalidate()` makes the next draw paint. `hits()` and `misses()` count one cache's draws; `takeTotals()` gives every cache's hits, misses and prims appended from a cache since the last call (`Context::buildFrame` takes them into `FrameStats`). A view draws its steady part through its cache, then what changes every frame on top, in the same drawing order as before, which the goldens check. The verifier is `VYBN_VERIFY_CACHE` (see Commands): with it set every draw paints, and when the key matched, the paint is compared with the kept section (its prims, plot values and hash), warning once per cache. Main thread only.
- **`Font`** (`Font.h/.cpp`): CPU-side. Bakes printable ASCII at each of the theme's font sizes into one `R8` coverage atlas with stb_truetype (2x2 oversampling; the atlas starts at 256x128 and doubles its height, then its width, until it fits: 2048x1024 today), and does measurement, metrics, kerning, and glyph layout. Other characters draw as `?`. Kerning is a 95 x 95 table of the printable characters' pairs (font units, filled once when the font loads), which measurement and layout read in place of a stb_truetype lookup per pair, with the same widths.
- **`Font`** bakes a fixed list of sizes (11 to 56 px): 2x2 oversampled below 24 px, 1x1 from 24 px up.
- **`UIRenderer`** shares its shaders, its pipeline and the atlas's texture (`UIRenderer::Shared`) with every other UIRenderer on the same device, swapchain format and font, so another window only adds its own set 0s and buffers (prims and plot data, one of each per frame in flight, grown on demand). It draws the `DrawList` with one pipeline and no scissors. Set 0 is per window and per frame in flight: the font atlas at binding 0, and at binding 1 a storage buffer of that frame's plot data (every plot's values in the frame, in order), grown on demand; a bigger buffer is pointed at by the frame's set at once, and the set is rewritten then, which is safe after `beginFrame`. Set 1 is the image being drawn, or a blank transparent 1x1 picture when none is, so set 1 is always bound. Each maximal run of non-image prims is one instanced draw of six vertices per prim, and each image prim is a draw of its own with its picture at set 1 (no pipeline change), so a frame is one pipeline bind and a draw per run between images. The `Prim` struct in `Prim.h` must match the inputs of `shaders/prim.vert`.
- **`shaders/prim.vert` and `prim.frag`** draw every kind. The vertex shader builds a six-vertex quad per prim: a surface's rect grown by its shadow (its distance times sqrt 2, its blur and a pixel, for a raised one; a pixel for the others), a Line plot's rect grown by its half width plus a pixel (the other plot modes by a pixel), and any other prim's rect as it is (a Line's rect being its capsule's bounds). It clamps every corner to the prim's clip, so nothing outside the clip is rasterised, which is the coverage the scissor used to give. It passes the local position (surfaces, from the centre; lines, absolute; plots, from their top-left) or the uv recomputed from the clamped corner (glyphs and images), unpacks the colours with `unpackUnorm4x8`, and passes the rest as flat varyings. The fragment shader branches on `kind`: a Glyph is the atlas's coverage times its colour's alpha, with the colour linearised; an Image is its picture, sampled with `textureLod` at level 0 and linearised; a Line is the distance to its capsule, anti-aliased across its edge (no texture); a Plot reads its values from the plot data, by its mode: a Line is the distance to the nearest of the three segments around the pixel's column, or where several values share a pixel, the bar between the lowest and highest of them (at most 64 sampled, and the two neighbours); a Fill is the area between the curve and its baseline, its edge anti-aliased by its distance; a Range is the pixel's column's bar, anti-aliased on its four sides; a plot's colour is linearised like every other kind's. A Surface is the neumorphic body described here. A surface's distance and its derivatives (which give the normal the rim uses) are taken before the branch, for every kind (zero distance for the others), so the derivatives stay in uniform control flow. Surfaces: a rounded-rect (or triangle or cross) distance field. `Raised` surfaces get light and dark shadows offset along the per-surface light direction, `Inset` surfaces get inner shadows, curvature adds a gradient across the face, and the rim lights the edge within about 1.5 pixels of it (by the outline's distance gradient against the light direction). The rim's strength travels in the fraction of the elevation attribute (elevation + rim x 0.45). Colours are sRGB and are linearised in the shader. `Elevation`'s enum order matches the shader's encoding (0 raised, 1 flat, 2 inset). The `style` input carries the light direction, curvature and form (0 rect, 1 triangle right, 2 triangle left, 3 cross, 4 triangle down, 5 triangle up).
- **Images**: `ImageData` (`Image.h`: a unique `id`, width, height, packed 4-byte BGRx `pixels` and a `version` the owner bumps) is drawn with `DrawList::add(ImageDraw{rect, image, opacity})`, which adds an Image prim. The UIRenderer keeps a `LiveTexture` and descriptor set per frame in flight for each image id (`liveImage`), rewrites this frame's when the version moved, remakes them when the size changes (after waiting for the GPU), and lets them go a few frames after the image was last drawn. The first pass of `render` brings every image up to date before anything is drawn. Live textures use a nearest sampler, so a picture drawn at its size lands pixel for pixel. If a live texture can't be made, images are skipped from then on.

- **`ProjectStore`** (`ProjectStore.h/.cpp`): the project with every change to it passed through it. Readers get `const Project &`; a change goes through an edit call (`edit()` for anything, including tracks added or removed, `editTrack`, `editMix` for a track's name, gain, pan, mute, solo, armed, folded, monitor and input only, `editClip`, `editMasterEffects`, `editExportPresets`, `editExportMetadata` (the export presets and details: only `revision()` moves), `editSettings` (ONLY the name, beats per bar and length: only `revision()` moves, not the structure), `select`, `setTempo`, `setLoop`, `toggleLoop`, `replace`, `restore(plan)`), which counts it as changed at once. `normalizeIds()` (`Project::normalizeIds` with the session's high-water mark, `nextId_`, so an id is never reused across `replace`, undo and redo) runs on construction (silently: the starting project is revision 1), on `replace`, at the start of `AudioBridge::sync`, at the start of DawApp's first FrameHook and before saving. - **`History`** (`History.h/.cpp`): undo and redo for the whole project, by snapshots. Nothing records itself: once a frame `DawApp` hands it the project, and when the content differs from the last state recorded (`sameContent`: tracks, clips, notes, mix, tempo, project settings and export presets and details (named "Edit export preset" and "Edit export details"); not the selection, note selection, arming, folding, monitoring or ids) and the edit has settled (no mouse button held, no text field focused, not recording or exporting), the last state becomes a step named by `describeChange` ("Delete notes", "Move clip", "Mute notes", "Edit Mod wheel", "Track volume"; controller lanes are compared too, the loop isn't, and undo keeps the loop as it is now). So any new edit anywhere is undoable without knowing about it. `canMerge` joins a step to the last one when it is the same kind within half a second and no mouse was used (held keys, the wheel). A selection-only change updates the state, so undo puts the selection back as it was. `undo(store, now, plan)` first records a change still waiting; `redo(store, plan)` refuses once an edit has replaced what could be redone (judged by the store's revisions). At most `kMaxSteps` (200). Steps are `Snapshot`s in two levels: the project's own fields, and per track a shell (`shared_ptr<const Track>`: everything but the clips) and its clips (`shared_ptr<const Clip>`), each shared with the neighbouring step when identical (notes' selection included), so a step costs what it changed (`storedClips()`, `storedBytes()`). The last state recorded is kept in the same form, so a selection change or an edit waiting to settle copies nothing. `update(store, ...)` remembers the store's revisions as of that state and compares only the tracks whose `trackRevision` or `mixRevision` moved (every track, by index, when the structure moved), the project's fields only when `revision()` moved and the master's effects only when `masterRevision()` did; once a difference is seen on an unsettled frame it stops comparing until the settled one, and the step's label is worked out from the changed tracks alone. `update(project, ...)` is the same core with every track treated as moved (tests, and undo's own look). `undo` and `redo` return a `HistoryRestore` plan instead of a project: `structural` (the track count or the id and kind order differs) carries the whole project to replace with; otherwise it holds the fields that differ and the tracks whose parts differ (found by pointer, confirmed by comparing), each with whether its content and its mix changed. `ProjectStore::restore` applies it, then `adopt(store)` takes the store's revisions as the state's, so the next frame compares nothing. `matches(project)` says whether a project has the state's content; `current()` unpacks the state (not for per-frame use). `reset` when a project is opened or made. It is fed through `ProjectSession::recordHistory`, which runs `update` only while a store revision (or the selection's) moved since the last call, or a change is still waiting to settle; an idle frame costs two integer reads.

- **Routing in the app** (`Routing.h/.cpp` in `src/daw`; design notes `docs/routing-plan.md`): `TrackKind::Return` and `TrackKind::Group` are buses (`isBus`, `Track::bus()`): no clips, no instrument, no recording, a chain of effects, a fader, pan, mute, solo and automation. `Track::output` is a group's id (`kNoId`: the master); `Track::sends` (`Send`: the id of a bus, a return or a group, a level 0-1 on a fader's taper, pre or post fader) holds only the sends that exist. Both are mix fields (`editMix`; undo steps "Route track", "Add send", "Remove send", "Change send"). A send's lane is a track's own lane with the id `sendParam(to)` (`0x40000000 + id`; `isSendParam`, `sendTarget`). `Project::masterVolume` (0-2, `editMasterVolume`, the master's revision; "Master volume") plays after the master effects, and `Project::masterAutomation` (the volume's lane, `editMasterAutomation`, the master's revision; undo "Edit automation"; saved as `master_automation = [{ param = "volume", points }]` at the root, read with a track's clamping and refusals, a pan, send or id lane refused) automates it. The rules: `reaches`, `canOutputTo` and `canSendTo` (the right kind, not itself, nothing that brings a track's sound back to it; a send may go to a return or a group, so one track can feed several buses, but never to the group the track outputs to, which would play it twice, and an output never goes to a group the track sends to; at most `audio::kMaxSends`, 64, sends per track, which `routingError` refuses past and `canSendTo` stops offering), `outputChoices`, `sendChoices`, `alsoToChoices` (the groups the Also to menus offer: those sent to and those that may be), `groupSends`, `setAlsoTo` (ticks or unticks a group: a post-fader send at 0 dB, or the send and its lane out, one edit), `removeSend`, `outputLabel` ("To Group 1 + 2": the groups also sent to, returns not counted, the name cut with ".." to 17 characters), `extraDestinations`, `groupSendLabel` ("G1"), numbered when two groups' short names match ("Dr1", "Dr2"; `groupSendLabel(project, group)`), `outputName`, `returnLetter`/`returnLetterOf` (returns go by A, B, ... AA), `forgetTrack` (a deleted track's sends, lanes and the outputs into it; `Project::deleteTrack` calls it) and `routingError` (the file reader refuses projects with one). `planRouting(project, latencies, maxDelay)` gives the engine its plan: routes the rules refuse or that would loop dropped in track order, each track's stage, every path's delay, and solo (a soloed track's sources and destinations are heard too, so its group and returns play and a soloed group plays its tracks). `AudioBridge::syncRouting` remakes the `audio::Routing` when the processors, kinds, outputs, sends, solos or latencies change (a hash), sets the compensations and solos from the plan, and only then takes the tracks that went out of the graph (`retiring_`, so no routing names a removed processor); it sets the send levels and the master volume every frame. - **`RenderJob`** (`RenderJob.h/.cpp`): the offline render an export runs. `OfflineEngine` is a deviceless `AudioSystem` with its own `RealtimePool` (half the cores less one, normal priority, its threads marked offline; `pooled` false mixes on the render thread alone, which the self-test compares against), a `MidiHub`, a private `ProjectStore` holding a snapshot of the project (every track disarmed) and an `AudioBridge` over them, with the snapshot's master effects and the live master gain. `prepare(waiting)` runs once a frame on the main thread until it returns true: the graph is synced, every library instrument and sound file is in, and no plugin is settling; its chains and plugin slots are set offline (the global offline flags are not touched, so the live engine keeps playing). `beginRender(startBeat, tracks, preFader, unmuted)` taps the listed tracks (`TrackProcessor::setTap`) and settles for a quarter second, then plays from `startBeat`; `render` takes up to 4096 frames of the master, and `tapLeft`/`tapRight` give a track's tap for the last call. `RenderPass` renders one set of `PassOutput`s (the master, or the listed tracks summed, cut to a range and a tail that ends after a fifth of a second below -80 dB) into float temp files, measuring each with `LoudnessMeter` and `TruePeakMeter`, on the background thread that owns the engine. `cancel()` stops it within a block and deletes its files. A pass has one sample rate, one tap kind (pre- or post-fader) and one mute rule (outputs that ignore mute and solo need `unmuted`), so a job runs one pass per group: `setRate` (main thread only, between passes) prepares the graph at another rate, and `prepare` waits for plugins to settle, so the render thread never reads a plugin's state. `renderReady` is the readiness check the exporter waits on. The export self-test (`renderChecks`) checks the demo master rendered with the pool against one with no pool (within 1e-6), the stems against the dry mix, a cancelled render, and reports the speed. Finishing: `RenderJob` runs the whole export of a preset. It expands the targets into outputs (EachTrack: one per track with notes or audio; Tracks: the chosen tracks summed; MIDI: `writeMidiFile` from the snapshot), groups the audio outputs into passes by rate, tap and mute rule, and is driven once a frame on the main thread: `update()` makes the engine (or sets its rate), waits for `prepare()`, starts the pass on a Background job, and when it has ended starts one finishing job per output, which runs while the next pass renders. A finishing job reads the output's float temp file in 65536-frame chunks: gain (Peak: target minus the sample peak, or the true peak when the limiter is on; Loudness: target minus integrated, and with the limiter on the gain is corrected by the miss up to three times, keeping the best, before the file is written; Off: none), fades, the limiter (only when `limiter` is on and normalize isn't Off), mono, dither (16 and 24-bit), then the encoder with the project's metadata, and measures the final signal into a `TargetReport` (bytes, length, integrated LUFS, LRA, short-term maximum and series, true and sample peak, gain applied, clipped samples). `RenderJob::state()` is `Preparing`, `Rendering`, `Finalizing`, `Done`, `Failed` (some output failed; the reports say why) or `Cancelled`; `fraction()` weights the renders 80% and the finishing 20%; `status()` says what it is doing; `reports()` has one per output; `cancel()` returns at once and the job becomes `Cancelled` once its jobs have let go; its temp folder (`%TEMP%\VYBN export\<id>`) is removed when it ends. Destroying a job waits for its jobs, then frees the engine on the main thread. `ExportQueue` (`enqueue(snapshot, preset, masterGain, outputFolder)`, `jobs()`, `active()`, `update()`, `cancel(id)`, `remove(id)`) renders one job at a time, in order; an output without a folder of its own goes beside the saved project (passed in), else the library's `Exports` folder. `queueChecks` in the export self-test runs the queue through the environment's loop: the Release preset's loudness, true peak and FLAC against its WAV, Release and Stems together (timed), the MIDI preset, two sample rates in one preset, 16-bit WAV against FLAC, a loud mix at -9 LUFS under the limiter, a repeated name (numbered " (2)" and noted), and a job destroyed mid-render.

Undo: the first `FrameHook` feeds the `History` each frame (settled when no button is held, no text field is focused, and not recording or exporting; not while a restore is waiting, `restoring_`). `undo`/`redo` (Edit > Undo and Redo, labelled with what they do; `edit.undo` Ctrl+Z, `edit.redo` Ctrl+Shift+Z and Ctrl+Y; ignored mid-drag, while typing, recording or exporting) get the history's `HistoryRestore` plan and post `restore(plan)`, which sets the transport's tempo only when the plan changes it and gives the plan to `ProjectSession::restoreState`: only the tracks, fields and selection that differ are edited (undoing a one-note edit moves one track's revisions, so the bridge sends one track's notes and the views redraw one track), arming, monitoring and the loop are left as they are; a plan that adds, removes or moves tracks replaces the project, keeping arming and monitoring by track id, and the bridge's sync matches the tracks by id, so a kept track keeps its processor and plugins (a track that is made again gets its instrument back from the library's cache). Nothing records history while `restoring_` is set. Export is `Exporter` (above). It owns an `AutosaveController` (`Autosave`): `update` runs in the first FrameHook each frame with the same `settled` as the history, writes the session lock on its first frame and whenever the project's path changes, and reports autosaves in the notice line; its destructor (the window closing, or Quit, returns from `Environment::run` and destroys `DawApp`) waits for a write under way and removes the session lock, so a kill leaves it for recovery. It owns the `Settings`, the `InstrumentLibrary`, the `OnlineCatalogue`, the `Downloads` and the `AssetBrowser` (opened as an overlay after the menus; View > Browser and Tab toggle it). The browser's previews are a `PreviewPlayer` (below), forwarded by `previewInstrument`, `previewSound`, `stopPreview` and `previewing`. `useInstrument` sets the selected instrument track's instrument or makes a track for it; `addSound` imports a file at the playhead; after a download installs an instrument, tracks that asked for it load it. Settings (`openSettings`) is a dialog with a sidebar (a `ListView` of section items) beside a `Pages` of one `ScrollView` per section: Audio, Recording, Sample library, Performance, Online, Saving and Keyboard. Each section is its own block in `openSettings`, built with the `page(name)` helper. Settings has a Performance section (`buildPerformanceSettings`: mixing threads, streaming long samples, the stream memory, letting overlays hook in, using Windows' file dialogs, how long unused sounds stay loaded, the sample cache's folder, and live figures from the memory manager and each lane) and an Online section: the Freesound API key, a link to get one, and Edit sources (writes the defaults to `sources.toml` the first time and shows it). An instrument track's processor gets a `NotePlayer` with a `Sampler` (gain 0.5, since samples are near full scale and notes overlap) as its source. The arrangement, the mixer and the editor are `DockPanel`s in a `DockSpace` (`dock_`, which fills the body under the transport bar): by default the arrangement over the mixer, with the editor as the mixer's other tab. Each can be torn off into a floating window and docked anywhere in the grid; the arrangement's tools (Follow, zoom, Add track) and the editor's status are in their panels' headers. `showMixer`/`showEditor` show that panel's tab (or raise its window) and set its place's share of the split (double-clicking a clip opens the editor). The layout isn't saved. `importInstrument` runs the system open dialog from a posted action, imports the files and, if the selected instrument track has no instrument, gives it the new one. `studioTheme(dark)` is the DAW's theme: shallower shadows than the default (depth 3, softness 1.6), so the minimum gaps stay small in a dense layout. A zero-size `FrameHook` at the top of the body runs first each frame. It sets `ui.setBusy(...)` (the loop's fastest idle pace, see UISystem) while the transport plays, a take records or finishes, a count-in runs, an export job is active (`exporter_->queue().active()`), a download is active, the browser's preview plays, a plugin slot is busy (loading or reloading, `Slot::busy()`), or a sample set is loading (`InstrumentLibrary::anyLoading()`). An open plugin interface (a device view showing its interface) and an armed audio track (its input meter) set busy too, so their pictures and meters refresh at the full pace; with neither, the pictures refresh at the idle pace (up to 10 a second). It reads the output peaks once into `StereoLevels` (`AudioSystem::takePeak` has one reader; every meter shows the copy), runs `syncTracks`, which calls the bridge's `sync` (adds a processor for each new track, copies every track's gain, pan, mute and solo to its processor, reads each track's peak into the bridge's `levels()` for the channel strips, sends an instrument track's notes as a new `NoteSequence` whenever their hash changes, loads the track's instrument from the library when it changes and hands it to the sampler, and runs each player's `collect`). Every keyboard command is a keymap action: `defineActions` adds them before the menus are built, `loadKeybinds` applies the user's changes, and the menu items name them, so the menu bar runs them (Space plays because Transport > Play / pause is `transport.playPause`). `showShortcuts` (Help > Keyboard shortcuts, F1, and a button in Settings) opens the shortcuts editor, which saves through `saveKeybinds`. `addTrack` changes the tree, and the arrangement and the mixer rebuild themselves when they see it.

`radial` is a track header's toggles opened as a radial menu (under a `StillContainer`, not an overlay, so the real mouse can't hover it), and `radialToggleChecks` drives an open `RadialMenu` (drag onto a button and let go, let go on the middle then click, the middle closing it); `folding` is the nested-groups arrangement (a golden and a cache scene), `foldChecks` and `foldUiChecks` fold on a laid-out `ArrangementView` (rows below moving up by the hidden rows' heights, `trackAt` never finding a hidden track, the chevron's click, indentation by depth, the folded counts, the selection unfolding once, Fold all and Unfold all, `FoldState`'s version) and `foldMixerChecks` counts a `MixerView`'s strips as groups fold, and `foldDragChecks` opens a folded project (its tracks hidden) and drags headers by input (a folded group moving with its tracks, a track dropped among hidden ones landing before the group); `sidechain` is the Devices panel on a pad with a keyed Compressor (a golden and a cache scene), `sidechainUiChecks` and `sidechainDeviceViewChecks` drive a real `DevicesView` and `DeviceView` (the choices, a choice as one undo step, the caption, renaming, adding and deleting tracks, undo, the master's, the limit's note), and `VYBN_TEST_BENCH` times the offers on a 64-track project (`INFO sidechain bench:`).

### Engine layer (`src/engine/`)

The UI layer and the application talk to these classes:

- **`WindowSystem`** (`WindowSystem.h/.cpp`): the windowing daemon. `open(title, w, h, WindowOptions{vsync, customTitleBar})` creates a `Window` and its `Renderer` and returns a `WindowId`. It publishes `WindowOpened`. The first window is the main window. `window(id)`, `renderer(id)`, `setCaptionTest(id, fn)` (looked up on every hit test, so it can be set after opening), `setCloseHandler(id, fn)` (asked when the user closes it; false keeps it open), `WindowOptions::visible`, `isVisible(id)` (false while minimised), `close(id)`. Each tick pumps OS events for every window, or sleeps 50 ms when none is visible, then handles closed windows. `setNextWait(seconds)` (the UI sets it each tick; it applies to the next tick only) makes a visible window's tick sleep in `waitEvents(seconds)` instead of polling, so the loop idles between changes; input and wakes end the sleep at once. Closing the main window stops the Environment. Other windows publish `WindowClosing` and are destroyed.

- **`Window`** (`Window.h/.cpp`): RAII over a GLFW window. The constructor opens it and the destructor closes it. GLFW is initialised by the first window and terminated when the last one closes. `Window.h` doesn't include GLFW, so only `Window.cpp` and `Renderer.cpp` see GLFW headers. Input arrives through GLFW callbacks (keys, characters, mouse buttons, cursor moves, the wheel) and is queued in order as `engine::InputEvent`s (`InputEvents.h`) until `takeEvents()` collects them; nothing is lost between frames. `cursorPosition`, `mouseButtonDown` and `modifiers()` poll the current state, `setCursor(engine::Cursor)` sets the pointer's shape over it (the system's standard cursors, made once and freed when GLFW terminates), and `clipboardText`/`setClipboardText` reach the clipboard. `position`/`setPosition`/`setSize`/`focus`/`show`/`setOpacity` place and show windows (a `Window` can start hidden), `desktopCursor` and `primaryButtonHeld` read the mouse anywhere on the desktop, `cancelClose` takes back a close the user asked for, and `waitEvents(timeout)` sleeps when nothing is visible. `time()` is the GLFW clock. `takeRefreshRequested()` says whether the system asked for a redraw since last asked (the GLFW window refresh callback: exposed, restored). The cursor is in window coordinates, which `ui::Context` scales to framebuffer pixels.
  - `useCustomTitleBar(isCaption)` (Windows only; elsewhere a no-op returning false) removes the system title bar. It hooks a window procedure in front of GLFW's: `WM_NCCALCSIZE` makes the client area the whole window (kept on screen when maximised), and `WM_NCHITTEST` returns resize edges, `HTCAPTION` where `isCaption(x, y)` says so (window coordinates), or client. A one-pixel DWM frame keeps the shadow. Snapping, edge resizing and double-click maximise stay native. Call it before creating the `Renderer`, so the swapchain starts at the final size. `minimize()`, `toggleMaximize()`, `isMaximized()` and `requestClose()` back the title bar's buttons. While Windows runs a native drag or resize the app's loop is paused, so the content doesn't redraw until it ends.
- **`Renderer`** (`Renderer.h/.cpp`): one window's Vulkan, on an instance and device every window shares (`SharedDevice`, made by the first Renderer and destroyed with the last; another window must present from the same queue family). `device()` and `format()` say which device and swapchain format it has, so resources made through one Renderer can be used with another. `setOverlaysAllowed(bool)` (before the first Renderer) decides whether the loader loads implicit layers: off, it sets `VK_LOADER_LAYERS_DISABLE=~implicit~` unless the user set a `VK_LOADER_LAYERS_*` variable (on this machine Steam's, Epic's, GOG's, Overwolf's, OBS's, Medal's and vkconfig's override, which forces the validation layer on, cost about 75 MB). With `deferSwapchain` the first `beginFrame` makes the swapchain; `releaseSwapchain`/`hasSwapchain` let a hidden window drop it. Memory on this machine (AMD): the instance about 28 MB and the first swapchain about 48 MB of driver state, whatever the window's size; the app is about 100 MB in all. Per window it owns the surface, swapchain, render pass, framebuffers, command buffers, and sync objects. It creates `Shader`, `Pipeline`, `Buffer`/`VertexBuffer`, `Texture`, `DescriptorSetLayout` and `DescriptorPool` objects, and drives the frame loop: `beginFrame()`, then `bind()` and `draw()`, then `endFrame()`. Swapchain recreation on resize or minimise is handled inside `beginFrame`/`endFrame`. It uses two frames in flight, one swapchain-image semaphore per image, and vsync (FIFO) unless created with `vsync = false` (then mailbox, else immediate, else FIFO). The viewport and scissor are dynamic. `drawInstanced(buffer, vertexCount[, firstInstance, instanceCount])`, `pushConstants(pipeline, data, size)` and `bindDescriptorSet(pipeline, set, index = 0)` (the set goes at that index of the pipeline's layouts) support the instanced UI draws. `setScissor`/`clearScissor` clip them (`beginFrame` resets the scissor), though nothing uses them now that the UI clips in its shader. `createTexture(width, height, format, pixels, size)` uploads through a staging buffer and a one-off command buffer, and blocks until done, so call it at load time. `swapchainGeneration()` counts the swapchains made and let go, so the UISystem presents again after one is replaced. `beginOffscreen(width, height)` and `endOffscreen()` draw a frame into an image of its own, cleared to the clear colour, and read it back as BGRA bytes, top row first (the render self-test's pictures); they work on a window with no swapchain. `recording()` (private) is the command buffer being recorded, this frame's or the off-screen one.
- **`Shader`** (`Shader.h/.cpp`): loads a SPIR-V file into a `VkShaderModule`. The stage is set when it's created.
- **`Pipeline`** (`Pipeline.h/.cpp`): a graphics pipeline from two shaders, a `VertexLayout` (stride, attribute formats and offsets, and a per-vertex or per-instance input rate; attribute location is the array index), and `PipelineOptions` (alpha blending, push constant size, and `descriptorSetLayouts`, a list with one layout per descriptor set from set 0; the UI's prim pipeline has two). It renders triangle lists with no culling.
- **`Buffer` / `VertexBuffer<T>`** (`Buffer.h/.cpp`): a persistently mapped, host-visible, host-coherent buffer. It's movable, and its contents are replaced with `write()`. Per-frame data should use one buffer per `Renderer::kMaxFramesInFlight`, indexed by `frameIndex()` and written after `beginFrame()`. Buffers themselves have no staging upload; textures do.
- **`LiveTexture`** (`Texture.h/.cpp`): a texture rewritten while in use (a plugin's interface): a linear-tiled image in host-visible, coherent memory, kept mapped in the GENERAL layout, so `write(pixels, width, height, stride)` is a plain copy. Keep one per frame in flight and write this frame's after `beginFrame`. `Renderer::createLiveTexture(w, h, format)` makes it and moves it to GENERAL once (blocking); `supported(physical, format)`; `DescriptorSet::writeTexture` takes one too.
- **`Texture`** (`Texture.h/.cpp`): a device-local, optimal-tiling 2D image with its view and a linear, clamp-to-edge sampler. Movable. Fill it through `Renderer::createTexture`, which leaves it in `SHADER_READ_ONLY_OPTIMAL`.
- **`DescriptorSetLayout`, `DescriptorPool`, `DescriptorSet`** (`Descriptors.h/.cpp`): a layout is a list of `DescriptorBinding`s (type and stages; the binding number is the array index). The pool holds combined image samplers and storage buffers: `Renderer::createDescriptorPool(maxSets, maxTextures, maxBuffers = 0)` and `DescriptorPool(device, maxSets, maxTextures, maxBuffers)`, `maxBuffers` storage buffers between the sets (a binding of type `VK_DESCRIPTOR_TYPE_STORAGE_BUFFER` takes one; `createBuffer` usage may include `VK_BUFFER_USAGE_STORAGE_BUFFER_BIT`). Sets are plain handles, freed with their pool; `writeTexture(binding, texture)` points one at a texture, and `writeBuffer(binding, buffer)` points a storage-buffer binding at the whole of a buffer. Both should only be called while no frame in flight uses the set.
- **`Http`** (`Http.h/.cpp`): `httpGet(request, sink, error, status)` over WinHTTP (HTTPS, redirects, the system's proxy, a `VYBN/1.0` user agent; `HttpProgress` has bytes done and total and a cancel flag), `httpGetText` (up to 16 MB) and `httpDownload` (into `<path>.part`, renamed when complete), and `urlEncode`. They block: call them from a background thread. Elsewhere than Windows they fail.
- **`Shell`** (`Shell.h/.cpp`): `openUrl` (the user's browser), `showInFolder` (Explorer with the file selected) and `runProgram(args, exitCode, error)` (no window; waits).
- **`FileDialog`** (`FileDialog.h/.cpp`): Windows' own dialogs, now only a fallback (the app uses `ui::FileDialog`): `openFileDialog(title, filters, multiple, folder)` and `saveFileDialog(title, filters, folder, name, extension)` (adds the extension when the typed name has none, and asks before replacing a file) (`GetOpenFileNameW`/`GetSaveFileNameW` over the active window; elsewhere they return nothing). They block, so call them from a posted action. And what the in-app dialog reads: `listFolder(path, entries, error)` (`FolderEntry`: name, folder, size, modified in seconds since 1970; one `FindFirstFileExW` pass with large fetches, hidden and system entries left out; it blocks, so from a job), `knownFolder(KnownFolder::Home/Documents/Desktop/Downloads/Music)` and `drives()` (the letters there now with their kind, without touching the drives, so an empty card reader can't stall it).
- **`Vulkan.h/.cpp`**: `check(VkResult, what)`, which throws `std::runtime_error` on failure, and `findMemoryType`.

Lifetime rule: every `Shader`, `Pipeline`, `Buffer`, `Texture`, descriptor layout or pool, and `ui::Context` must be destroyed before the `Renderer` it came from, and the `Renderer` before its `Window`. The daemons keep this. The `WindowSystem` holds each window and renderer (renderer destroyed first) and is added before the `UISystem`, which holds the Contexts, so the Environment destroys the UISystem first. A window closed while running publishes `WindowClosing` first, and the UISystem drops its Context then.
